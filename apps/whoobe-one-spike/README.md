# whoobe-one-spike — Phase 0 + 1 + 2 + 3 (partial) of the whoobe-one-studio Vue 3 port

Standalone spike, not wired into any other app in this monorepo. Phase 0's job was to answer the porting plan's highest-uncertainty question: **does the source repo's core loop — click an element to select it, click into its text to edit it in place via native `contenteditable`, drag it into a different container — actually work under Vue 3?** Phase 1 ported the surrounding data/state layer (pure-data scripts, the remaining four Vuex modules, hotkeys, routing). Phase 2 ported the rest of the core editing UI - the four remaining `Vue.prototype.$x` plugin files, the real "add element" sidebar, and rich-text editing - and was the first phase where most of what got ported in earlier phases while dormant (`DatabaseClass.js`, `animations.js`, `editor.elements`) actually got exercised by something real. Phase 3 (panels/dialogs/gallery) has only just started: the Tailwind customizer panel is built (jumped ahead of the rest of Phase 3 since it's the single most-requested headline feature and directly builds on `tw.classes.js`/`tw.groups.js`, ported in Phase 1 and dormant since) - dialogs, the snippet/UI-kit gallery, and the desktop shell are still not started.

See `docs/plans/cms/whoobe-one-studio-vue3-port-plan.md` §5 ("Phase 0 - Spike", "Phase 1 - Data & state layer", "Phase 2 - Core editing UI", "Phase 3 - Panels, dialogs, gallery") for the full plan this executes.

## Run it

```
pnpm --filter @pimcore-custom/whoobe-one-spike dev
```

Opens on port 3006. A demo document is seeded on load: a heading + paragraph side by side, an image, and a button, inside an outer container.

Try: click the paragraph, click into its text and edit it, click elsewhere to blur (check the text stuck); drag the image into the heading/paragraph row; use the toolbar to add a new Container then drag an element into it; delete a selected element.

## What's ported verbatim vs. rewritten

- **`src/scripts/ElementsClass.js`, `BlocksClass.js`, `DatabaseClass.js`** — byte-for-byte copies from the source repo (confirmed zero Vue coupling in the port plan). `BlocksClass`/`DatabaseClass` are copied per the plan's file list but not yet exercised by anything in this spike — no save/export/library UI exists yet, that's Phase 1+. `ElementsClass.js` is genuinely load-bearing: both the seeded demo document and the toolbar's "add element" buttons build real `Element` instances through it.
- **`ElementsClass.d.ts`** — a hand-written type shim next to the `.js` file (TypeScript's standard mechanism for typing an unmodified JS file). Needed because strict-mode TS infers dynamic fields far too narrowly from the class's own constructor/default-parameter literals (e.g. `image: { url: null }` infers as literally `{ url: null }`, not `{ url?: string | null }`) — a consequence of consuming legacy untyped JS under `strict: true`, not a bug in the source file or this shim.
- **`BlockElement.vue`, `BlockContainer.vue`, `BlockEditor.vue`** — rewritten fresh in Vue 3 `<script setup>` (not a mechanical Options-API line-by-line port), since the whole point of this app's existing convention (see `apps/whoobe-studio`) is `<script setup>`, and Phase 0's goal is proving the *interaction model* works, not preserving Options API structure. Deliberate deviations from the source, all commented in place:
  - `element`/`doc`/`level` are real declared `props`, not read off `this.$attrs` (the source's pervasive pattern, port plan §2 item 3).
  - The five `new Vue()` event buses collapse to a single `mitt`-based `editorBus` (+ an unused `dialogBus` stub) — port plan §2 item 1.
  - Selection hit-testing uses `@click.self` on each container instead of the source's z-index-ladder + absolute-overlay trick (`BlockElement`'s `classe` computed adding `z-{level+1}` specifically to out-rank the container's own click-catching overlay). `@click.self` gets the same "background vs. child was clicked" distinction natively, with no manual z-index bookkeeping.
  - One shared `dragula` instance lives in `BlockEditor.vue`, not one instance per `BlockContainer` (the source creates a new `dragula()` call in every container's `mounted()`, all with the *same* document-wide `isContainer` predicate — functionally redundant N instances managing the same global element set, not real per-subtree scoping).
  - Two real bugs in the source were fixed rather than reproduced: its drop predicates checked `el.getAttribute('type')`, but only containers ever set a literal `type` attribute (`type="container"`) — elements only ever set `data-type="element"`, never plain `type`, so the intended "only elements are draggable, not containers" constraint looked unenforceable as originally written. This spike uses `data-type` consistently on both. Separately, the source's dragula config key was `move:` (not a real dragula option — the real one is `moves:`), which would have silently done nothing.
  - **The one genuinely new problem this spike had to solve**: dragula physically moves the dragged DOM node into the drop target as part of its own drag UX, *before* our `drop` handler runs. If we then also push the corresponding data node into the target container's reactive array (which we must, to persist the reorder), Vue's own re-render creates a *second*, new DOM node for it — dragula's manually-relocated original node would be left behind as a duplicate. The fix (`BlockEditor.vue`'s `drop` handler): undo dragula's own DOM move immediately, so Vue's reactive re-render is the only thing that ever decides final DOM placement. This is a known, documented pattern for integrating dragula (or any vanilla DOM drag library) with a reactive framework, not something specific to this app.
- **`bus.ts`, `helpers.ts`, `store/editor.ts`** — new, small, and directly replace the slice of the source's `Vue.prototype.$x` global methods (`scripts/index.js`, `editor.js`) and Vuex `editor` module that these three components actually call. Everything else those files provide (settings, autosave, page/document distinction, export, purge, etc.) is out of scope here — Phase 1+.

## What's deliberately NOT here (later phases, not oversights)

- No dialogs (the `dialog/Dialog.vue`/`dialog/Modal.vue` bus-routed system), no snippet library UI (`templates.js` is ported and ready, unconsumed), no AlpineJS support.
- Most keyboard shortcuts are inert bus emits with nothing listening yet (see the Phase 1/2 sections) - delete, duplicate, copy/paste, and the seven quick-add shortcuts work today; the customizer/GSAP-picker/CSS-editor/shortcuts-help/preview hotkeys still don't (the Tailwind customizer panel itself is only reachable via its sidebar tab, not the Alt+Z hotkey).
- Whole-database export/import backup (`dexie-export-import`) and settings CRUD (`$settings`/`$saveSettings`) are real in `database.js` but not ported - no UI exists to drive either yet (Settings.vue is later Phase 3 scope).
- No real Dashboard (`views/Main.vue` is a one-button stub, not the source's Templates/UI-Kit/Settings launcher), no Templates/PagesGallery/UiKits gallery UI, no drag-in snippet library.
- Tailwind customizer: 5 of 14 control atoms ported (see the Phase 3 section for exactly which, and why several turned out to be one control in disguise) - position/gradient/font-family controls and the two already-commented-out-in-the-source text/background color pickers aren't there.
- Tailwind here is otherwise a stock v4 setup with the default theme — no attempt yet to reconcile the source's hardcoded, `postcss7-compat`-era utility class list (`tw.classes.js`) against Tailwind v4's real utility set beyond what the Tailwind customizer section above already surfaced (port plan §6, an open risk independent of the Vue port).

## Bugs found after the first "it typechecks and builds" pass

Two real runtime issues only surfaced once the app actually ran in a browser (not caught by typecheck or a clean module-graph fetch, since both are compile-time/transform-time checks, not runtime execution):

1. **`@apply` inside a component `<style>` block** (originally in `BlockEditor.vue`) needs Tailwind v4's `@reference` directive to know about utility classes at all - without it, the Tailwind Vite plugin throws `Invalid declaration` at transform time. Fixed by dropping the `<style>` block entirely and inlining the utility classes directly in the template instead.
2. **`Uncaught ReferenceError: global is not defined`**, thrown by `dragula`'s own dependency chain (`crossvent` → `custom-event`), which references Node's `global` object assuming a bundler that polyfills it - Webpack did this automatically for years, Vite/esbuild does not. Fixed in `vite.config.ts` with `define: { global: 'globalThis' }` **plus** the same define under `optimizeDeps.esbuildOptions` - the top-level `define` alone was not enough to reach Vite's dependency pre-bundling step for this dependency; both were needed. Confirmed by grepping the actual pre-bundled `dragula.js` (dev) and the production `dist/assets/*.js` output for literal `global.` reads - zero remaining in either after the fix.

Both were transient-looking errors reported live from an open browser tab while iterating - worth remembering for Phase 1+ that this class of bug (legacy CJS dependency assuming Node globals) is specific to *this* dependency (dragula) and should be checked again whenever a new dependency from the source repo's list gets pulled in (e.g. `dexie`, `@tiptap/vue-3`, `vue-codemirror`).

## Round 2: selection bug, empty containers, drag-to-add, image placeholder

Feedback after the first interactive pass surfaced a real bug and two real gaps:

- **The bug**: clicking a container's background to select it (`@click.self` on `BlockContainer`) worked, but the click event then kept bubbling - the outer canvas wrapper had a plain `@click="editor.setCurrent(null)"` "click empty space to deselect" handler, which fired right after and immediately cleared the selection that was just set. Fixed by making that outer handler `@click.self` too, so it only fires when the click target is genuinely that wrapper div itself, not a bubbled-up click that something deeper already handled.
- **Gap 1 - empty containers were invisible**: a brand-new container with no children yet has nothing giving it size, so it collapsed to a few-pixel sliver - technically selectable, practically impossible to find or click. Fixed with a `min-h-12 min-w-12` floor applied only while a container has zero children.
- **Gap 2 - toolbar "add" targeted "whatever is currently selected"**, which is exactly as fragile as it sounds: select a container, then click "+ Paragraph" elsewhere and the paragraph goes wherever `editor.current` happens to point at that moment - easy to get wrong, and was the direct cause of "adding a paragraph places it in the document instead of the container I just added." Replaced entirely with **drag-to-add**: the toolbar is now a fixed palette of draggable chips (`data-type="template"`), and dropping one onto any container creates a brand new element there via dragula's `copy` option (the palette item itself stays put - only a clone gets created in the drop target). This removes the "which container is secretly selected right now" question altogether; you drag directly onto the container you mean.
- **Gap 3 - images had no visible placeholder**: a freshly-created Image element had no `src` at all - invisible box, easy to lose track of. `applyImagePlaceholder()` (`helpers.ts`) gives new Image elements a self-contained gray-box-with-mountain-icon SVG data URI by default (no network dependency) - applied at the palette-drop call site, not inside `ElementsClass.js`'s own `Image()` builder, since that file stays a verbatim, unmodified port.

## Round 3: floating contextual action toolbar

Added `FloatingToolbar.vue` - the equivalent of the original app's `BlockFloatingAction.vue`/`BlockFloating.vue`: a small action bar anchored at the top-left corner of whatever is currently selected (container or element), shown/hidden purely by `editor.current`. Position tracks the selected DOM node's live `getBoundingClientRect()` every animation frame while something is selected, rather than wiring explicit scroll/resize listeners - simpler, and it correctly follows the element through content reflows too (e.g. editing text changes its height) without needing a `MutationObserver`.

Actions, shown conditionally based on what's selected (containers vs. text-editable elements vs. images):

- Move up (swap with previous sibling)
- Add child - containers only, adds a default Paragraph (the original's "Add element" opened a full picker; here you have the drag-to-add palette for anything beyond the common case)
- Direction row/column - containers only, toggles `flex-row`/`flex-col`
- Edit content - text-editable elements only, focuses the node (already always `contenteditable`, so this just places the cursor)
- Text color / Fill color - native `<input type="color">` swatches rather than a custom picker
- Image URL - containers (background image) or image elements
- Link URL
- Delete (replaces the old top-bar "Delete selected" button entirely - this is more discoverable and matches the original's design, where all per-node actions live on the floating bar, not a persistent toolbar)

Deliberately scoped down from the reference: real icon fonts (Iconify) are a Phase 2 concern - plain glyphs stand in here. Image/Link use a plain `window.prompt()` rather than the original's own picker dialogs (no `MediaUrlImporter`-equivalent exists in this spike). Font family/size picking is skipped entirely.

## Phase 1: data & state layer

Everything the port plan (§5) scoped for Phase 1:

- **Pure-data scripts ported to `src/scripts/`**: `templates.js` (the `Template` class - snippet builders, e.g. `hero()`/`cta()`/`navbar()`, all pure `Element`/chained-builder construction, confirmed zero Vue coupling), `tw.classes.js` and `tw.groups.js` (the Tailwind customizer's utility-class lookup tables and group/control config - feed Phase 3's `BlockTailwind.vue`, not consumed by anything yet), `animations.js` (18 `gsap.registerEffect()` presets - feeds Phase 2's `gsap.js` plugin port, not consumed yet). All three of these are currently *dormant* in this spike (ported and available, nothing imports them yet) - exactly like `BlocksClass.js`/`DatabaseClass.js` were in Phase 0, and for the same reason: the UI that consumes them is a later phase.
  - Two were **not** copied fully unmodified, and both deviations are necessary, not stylistic:
    - `grid.js` had `export default colSpans = {...}` with no declaring keyword - under `"use strict"` (which the file itself opts into), assigning to an undeclared identifier throws `ReferenceError` at import time. Fixed by declaring `const colSpans = ...` before the export.
    - `tw.classes.js` read `process.env.VUE_APP_FONT_FAMILIES` directly - Vue CLI/webpack's env convention, substituted at build time by `DefinePlugin`. Vite's own convention is `import.meta.env.VITE_X`, and `process` isn't defined at all in a Vite browser build by default. Changed to `import.meta.env.VITE_FONT_FAMILIES` (see `.env`/`.env.example`, copied from the source repo's own `.env.example` font list).
- **All five Vuex modules ported to Pinia** (`store/editor.ts` expanded to its full ~20-field shape, plus new `datastore.ts`/`desktop.ts`/`user.ts`/`generator.ts`) - confirmed flat/mechanical in the port plan (§1.4), one setter per field, Pinia collapsing the mutation+action two-layer indirection into a single function per field since Pinia doesn't need Vuex's layering. One forced rename: the source's `editor.export` field is `exportMode` here - `export` is a reserved word and can't be a variable/property identifier in this position at all (not a Vue-version issue, a JS-language one). `desktop.js`'s one real side effect (the `currentTab` setter writing to `localStorage`) was kept, not "fixed" - out of scope to redesign here.
- **`hotkeys.js` ported and actually wired up** (`App.vue`'s `onMounted` calls `setupHotkeys()` once) - not just copied. The source registers its `window.addEventListener('keydown', ...)` as an import-time side effect; ported here as an explicit function call instead, which is easier to reason about (and re-testable) than a side effect baked into module loading. Alt+R (delete) and Alt+1..7 (quick-add Grid/Flexbox/Heading/Paragraph/InlineText/Image/Button into the selected container) work for real right now, since they only need `ElementsClass`/Pinia, both already real. Everything else the source's hotkeys map defines (duplicate/copy/paste clipboard, the customizer, GSAP picker, custom-JS/CSS editors, shortcuts help, fullscreen preview) still just emits its bus event with nothing listening yet - faithful to the source's own scope for this file, not a gap this port introduced.
- **Vue Router 4** (`vue-router` added as a dependency): `router/index.ts` replaces `new VueRouter({mode:'history',...})`/`Vue.use(VueRouter)` with `createRouter({history: createWebHistory(), ...})` + `app.use(router)`. The source's `NavigationDuplicated`-swallowing monkey-patch on `VueRouter.prototype.push` was dropped, not ported - Vue Router 4 already resolves (doesn't throw on) duplicate/aborted navigations by default, and `VueRouter` is a factory function in v4 with no prototype to patch that way regardless. Two routes exist: `/` (`views/Main.vue`, a deliberately tiny dashboard stub - the source's real `Dashboard.vue` is Phase 3 scope) and `/editor` (`views/Editor.vue`, wrapping `BlockEditor.vue` - this absorbed the demo-document-seeding logic that used to live directly in `App.vue`). `/editor` wasn't an active route in the source's own router either (only `/` was) - added here specifically so this router demonstrates real navigation; a single static route wouldn't prove Vue Router 4 actually works end-to-end.
- **`App.vue`'s bootstrap** now mirrors the source's own `mounted()` hook more closely: populates `editor.elements` from `new Element().Groups()` (previously only exercised implicitly), in addition to installing hotkeys.

Everything the port plan (§5) scoped for Phase 2, plus what it unlocks:

- **`editor.js` ported as `scripts/editor-actions.ts`** (plain exported functions, e.g. `duplicateCurrent(editor)` instead of `this.$duplicateBlock()` - same rationale as every other plugin port this spike). Real, working: duplicate (Alt+D), copy/paste via a clipboard in `localStorage` (Alt+C/Alt+V - not actually a port, since the source's own hotkeys.js emits these with no listener anywhere in the surveyed codebase; this is the natural, obvious pairing), export-block/export-document/import-document as JSON (the top bar's Export/Import buttons), `beautify()` (ported, not yet wired to any UI - no code/HTML preview panel exists yet), `purgeCSS()` (ported, not yet wired - no build/export-static-page panel exists yet). One real bug found and *not* reproduced: the source's `$block_duplicate` (superseded by the working `$duplicateBlock` later in the same file) references a variable before it's ever assigned - would throw. Only the working version was ported. Also found: `jp.parent()` (not `jp.query()`) is what actually gives a live, splice-able reference to a node's parent array - `query()` returns a throwaway copy of just the matched element itself. Not ported: `$exportCustomLibrary` (needs the UI-Kit gallery, Phase 3), `$exportBuild` (the separate `whoobe-one-vite` static-export tool, out of scope entirely), `$exportImage`/`$imageInfo` (no new pattern beyond what's already proven).
- **`database.js` ported as `scripts/database-actions.ts`, and this is what finally exercises `DatabaseClass.js`** (ported all the way back in Phase 0, completely dormant since). Real Save/Load buttons in the top bar persist the current document to IndexedDB via Dexie and list/reload saved pages. `editor.page` (a `Block` from `BlocksClass.js`, another Phase-0-ported-but-dormant file) is now a real thing too - created alongside the seeded document in `views/Editor.vue`, mirroring the source's own `actions.js` pattern of `page.json.blocks` and `document` starting out as the same object reference. That implicit same-reference trick is fragile once `editor.document` gets wholesale-replaced (Import, Load) though, so `savePage()` re-syncs `page.json.blocks = editor.document` explicitly right before persisting, rather than depending on identity that Import/Load would otherwise silently break. Not ported: the whole-database export/import backup feature (`dexie-export-import`) and settings CRUD - both real in the source, both just have no UI to drive them yet.
- **`gsap.js` ported as `scripts/gsap-actions.ts`, exercising `animations.js`** (ported in Phase 1, dormant since - importing it is literally what runs its ~18 `gsap.registerEffect()` calls). Only `previewAnimation()` is ported (the source's simpler, immediate-play `$animationElement`) - the source's `$animation` is ScrollTrigger-driven, meant for the *exported static page* reacting to scroll-into-view, which doesn't mean anything for a node that's already on-screen while you're actively editing it. Wired into `FloatingToolbar.vue`: a new animation picker + "▶ Preview" button, storing the choice on the node's own `gsap.animation` field (so it round-trips through save/export) and playing it immediately for feedback.
- **`BlockElements.vue` ported as `BlockElementsPalette.vue`** - a real categorized/collapsible sidebar (containers/text/media/form, from `editor.elements`, populated via `Groups()` since Phase 1 but unconsumed until now) replacing the flat, hardcoded 6-item palette row from Phase 0. Drag-to-add uses the same `data-type="template"`/`data-template` attributes and shared `dragula` instance in `BlockEditor.vue` as before - but this introduced a real regression, caught after the fact: the `dragula-source-container` class ended up on the outer sidebar div, with each chip nested one level deeper inside a per-group grid wrapper. Dragula requires a draggable item to be a *direct* child of a recognized container - it walks up from the click target to find a container ancestor, then drags whichever direct child of that container was on the path, not the click target itself. With the class on the outer div, that direct child was the grid *wrapper*, which carries no `data-type` - so `moves()` correctly rejected it and nothing was draggable at all (the old flat palette row worked because each chip *was* a direct child of the marked container). Fixed by moving the class onto the actual grid wrapper div, one level closer to the chips.
- **`BlockTipTap.vue` + `BlockEditContent.vue` ported as `TipTapPanel.vue`**, using `@tiptap/vue-3` (official Vue 3 equivalent, same `Editor`/`EditorContent` API - port plan §2 item 8). Reachable from `FloatingToolbar.vue`'s "Edit content" button, but only for paragraph elements (`element === 'p'`) - exactly the same dispatch the source's `BlockEditContent.vue` makes (every other text type just gets the plain `contenteditable` path, unchanged). Shown as an inline modal `FloatingToolbar.vue` owns directly, since the source's own dialog-bus routing system (`dialog/Dialog.vue`) is Phase 3 scope. One real, non-obvious fix: `@tiptap/vue-3`'s `Editor` type didn't type-check against `EditorContent`'s `editor` prop when held in a plain `ref()` (a `vue-tsc` friction point around the class's private fields) - fixed by switching to `shallowRef`, which is also what Tiptap's own Vue 3 documentation recommends for the editor instance regardless (it manages its own internal reactivity; wrapping it in Vue's deep-reactive `ref()` is both unnecessary work and the source of that type friction).

### A real, broader bug this surfaced: most Range/Options values silently did nothing

Reported as "`p-[12px]` doesn't work, and `p-8` doesn't either, but `p-4` does." Root cause: Tailwind v4 only generates CSS for a class if it finds that class written out *literally* somewhere in the scanned source files (or explicitly declared via `@source inline()`) - it has no runtime awareness of classes a user types into a live, running app. `p-4` "worked" purely by accident - it happens to appear as a literal string inside `templates.js`'s snippet builders (ported in Phase 1, otherwise completely dormant/unconsumed - its *source text* still gets scanned regardless). `p-8` never appears literally anywhere in this codebase, so no CSS rule for it ever existed.

This isn't just a Custom Classes problem - it's the exact same silent failure for *every* Range/Options control in the Tailwind customizer, for any value that isn't coincidentally already used elsewhere as literal text. Padding, margin, gap, width, height, opacity, z-index, border-width - all of it, for whichever specific values this codebase's own source doesn't happen to also reference.

Fixed at the root, not just for `p-8`: wrote a one-off script that imports `tw.classes.js` itself and flattens every value out of every one of its arrays, then declared the *entire* resulting list (1012 unique tokens) via a single `@source inline()` in `style.css`. This guarantees every class the structured controls can ever produce has real CSS generated, regardless of what any other file's source text happens to contain. Verified concretely: `p-8`/`gap-6` now generate real rules in the compiled CSS; a few non-Tailwind tokens that are also present in `tw.classes.js`'s own arrays (bare color names like `"blue"` meant to be combined with a `bg-`/`text-`/`border-` prefix elsewhere, semantic tag names like `"article"`/`"nav"` used for an unrelated concern, custom z-index names like `"z-max"` that were never real Tailwind classes to begin with) correctly generate nothing at all - harmless, exactly like the already-confirmed `"bluegray"`/`"brown"` case above, not a new problem.

**What this does *not*, and structurally cannot, fix**: arbitrary bracket-value classes typed into the Custom Classes field, like `p-[12px]`. Those are unbounded by definition - there's no finite list to pre-declare for "any pixel value a user might ever type." This is a genuine architectural limitation of Tailwind's build-time, static-scanning model, not something an `@source` tweak can paper over.

### Superseded: switched to Tailwind's runtime/browser build entirely

The `@source inline()` safelist above (both the border-color one and the 1012-token dump) fixed *known, bounded* classes - but arbitrary bracket values were still structurally impossible under a build-time model, no matter how big the list got. Rather than accept that limitation, this app now runs Tailwind entirely differently:

- **`@tailwindcss/vite` (the build-time PostCSS/Vite plugin) is gone** - removed from `vite.config.ts` and `package.json` entirely, not just unused.
- **`@tailwindcss/browser` runs instead**, wired up in `main.ts`: it's a self-executing script (not a real ES module - loaded via a dynamically-created `<script>` tag, imported through Vite's `?url` suffix so it resolves to a real, working asset URL in both dev and the production build). Once loaded, it scans the live DOM immediately and keeps watching via a `MutationObserver` for as long as the page stays open - no rebuild step, no predeclared class list of any kind, works for genuinely any class because it's compiling in the browser, live, against whatever is actually in the DOM at that moment.
- **`style.css`'s `@import "tailwindcss"` and every `@source`/`@source inline()` declaration were removed**, not kept around unused - none of them do anything once nothing processes this file as a Tailwind entry point anymore.
- Confirmed no other file in this app relies on Tailwind-specific CSS at-rules (`@apply`, `@reference`) that only the removed build-time pipeline understood - grepped for both, zero matches, so nothing was silently broken by removing it.
- **Concretely verified** (as much as this environment allows without a real browser): production build's CSS output shrank from ~58 kB to 0.62 kB (confirming no build-time Tailwind generation happens anymore - the file now contains only this app's own two lines of plain CSS), the runtime script correctly appears as its own ~282 kB asset in the build output, and the `?url`-resolved path was confirmed to actually serve real, executable JS (not just a 200 with an unrelated body) in both dev and prod.
- **Real tradeoff, not free**: a noticeably heavier JS payload (~282 kB extra, unminified further by this app) shipped to the browser, and Tailwind's own docs explicitly don't recommend this approach for a *published/production* page - both acceptable here since this is an editing tool, not the final rendered output. The source app's own README already describes a separate export step (`whoobe-one-vite`) for producing a real, purged static page from whatever gets built in the editor - that path would still go through a proper build-time Tailwind pass of its own, separate from the editor's live preview.
- **Not yet interactively confirmed**: does `p-[12px]` (or any other arbitrary bracket-value class) actually render correctly now - this is exactly the kind of thing that needs a real browser to click through, which isn't available in this environment.

## Round 6: YouTube/Vimeo embeds were unselectable - clicking always started playback

Reported bug: selecting a YouTube/Vimeo element always started the video instead. Root cause, specific to running an iframe embed *inside a clickable editing canvas* (a problem the source app's own `BlockIFrame.vue` never has to solve, since it only ever renders in an already-static preview, not an interactive editor): an `<iframe>` is its own separate browsing context. A click that lands on its visibly-rendered content (e.g. YouTube's thumbnail/play button) is handled entirely by that embedded page and never bubbles up to the parent document at all - so the `@click` handler bound directly on the `<iframe>` (the previous approach, same as the generic elements) was structurally unreachable by a real click. In practice, every click just hit YouTube's own play button underneath the cursor and started the video; "select this element" never actually fired.

Fixed in `BlockIFrame.vue`: `data-id`/`data-type`/the click handler moved off the iframe onto a wrapping div, and the iframe itself now has `pointer-events-none` - every click lands on the wrapping div (always selectable, never triggers playback) and passes straight through the now-inert iframe. Since that also means the user can no longer click the embed's own on-screen play button at all while editing, `FloatingToolbar.vue` gained a new "▶ Play video" button (shown whenever a youtube/vimeo element with a video ID set is selected) as the deliberate, explicit way to start playback instead - it sends each provider's own postMessage player-control command (`{event:'command',func:'playVideo',args:[]}` for YouTube, `{method:'play'}` for Vimeo) to the iframe's `contentWindow`. This requires the query param each provider's postMessage API is gated behind (`enablejsapi=1` for YouTube, `api=1` for Vimeo) - added via a new `iframeSrc` computed in `BlockIFrame.vue`, appended to the existing `element.src + element.content` URL rather than touching `ElementsClass.js`'s own fixed embed-prefix.

Verified with clean typecheck and production build (224 modules, unchanged from Round 5 - both changed files are edits to existing components, no new files); both files confirmed transforming through the dev server. **Not yet interactively confirmed**: does clicking the video area now reliably select rather than play, and does the new Play button's postMessage command actually start playback in a real YouTube/Vimeo embed - needs a real browser to click through.

### Follow-up: raw postMessage didn't actually start playback

Reported after clicking the new Play button: nothing played, and the console showed `Permissions policy violation: picture-in-picture is not allowed in this document`.

Two real, separate issues:

- **The console warning**: `allow="...picture-in-picture"` on the iframe (copied over from the source's own boilerplate `allow` attribute, never actually used by this app) grants a permission the top-level page's own Permissions-Policy doesn't explicitly allow - logging a real, if harmless, violation on every embed. Reported: `Uncaught InvalidCharacterError: ... ('h[object Object]') is not a valid name`, from Vue's own `createElement` call. The source's only real call site for this (`helpers/Heading.vue`) passes `this.level` directly, never an options object; its palette (`BlockElements.vue`) calls `createElement(el.name)` with no second argument at all for everything else, letting `undefined` fall through to each builder's own default.

This app's drop handler always passed `{}` for every dropped template except Flexbox - harmless for builders that ignore the second argument entirely (`Paragraph`, `InlineText`, etc.) or that already expect an options object (`Flexbox`), but not for `Heading`: JS default parameters only substitute for `undefined`, not `{}`, so `this.level` became the literal object `{}` instead of `1`. `BlockElement.vue`'s `component` computed then evaluated `'h' + el.level` as the string `"h[object Object]"`, which the browser correctly rejects as an invalid tag name - a hard crash the instant a dragged Heading tried to render.

Fixed by only passing an options object for Flexbox (the one builder that actually needs one) and calling `createElement(templateName)` with no second argument for everything else, matching the source's own actual usage pattern. Verified directly, not just by inspection: called the real `createElement()` dispatcher both ways - `createElement('Heading', {})` (the old, buggy call) confirmed producing `level: {}` / tag `"h[object Object]"`; `createElement('Heading')` (the fix) confirmed producing `level: 1` / tag `"h1"`.

Verified with clean typecheck and production build (229 modules, unchanged - a logic-only edit to an existing file). **Not yet interactively confirmed**: does dragging a Heading chip from the palette now actually render correctly in a real browser - needs a real drag-and-drop interaction to fully prove, same gap as every drag-and-drop feature in this file; the underlying data-corruption bug itself was verified directly, not assumed fixed.

## Round 13: Save crashed with a Dexie DataCloneError - a pre-existing bug, not caused by the path prompt

Reported right after Round 12: `Uncaught DexieError2 { name: 'DataCloneError', message: "...#<Block> could not be cloned." }` when actually saving. Fixed in `database-actions.ts`'s `savePage()`: snapshot to plain JSON (`JSON.parse(JSON.stringify(editor.page))`) before calling `addPage()`/`updatePage()`, never store the live reactive object itself. Verified concretely: reproduced the *exact* `DataCloneError` on a `reactive(new Block())` wrapping a real nested `Element` tree via `structuredClone()`, then confirmed the same object survives `structuredClone()` cleanly once passed through the JSON-snapshot step first (round-tripping the nested Heading's `level` and the container's `tag` correctly).

## Round 29: custom nav classes silently lost to the built-in ones - a real Tailwind cascade bug, not a caveat

Reported directly after trying Round 27's Tailwind-class fields for real: setting `w-40 h-40 hover:bg-black/20 bg-transparent text-black/30` on an arrow button DID resize it, but the background stayed the built-in black and the hover color never changed. Round 27's own comment had already flagged a *theoretical* version of this risk ("two classes fighting over the exact same property can occasionally still lose to the built-in one") - this is that exact risk, now confirmed as a real, always-reproducible bug, not an edge case.

**Root cause, confirmed against the real engine, not just reasoned about**: compiled both class lists through `tailwindcss` v4's own `compile()`/`build()` API directly. When two utility classes set the *same* CSS property, the cascade winner is whichever rule's selector sorts later in Tailwind's own generated stylesheet - and Tailwind orders same-property utilities by its own internal canonical sort (alphabetical/numeric by class name within each property group), completely independent of which class appears later in the element's own `class` attribute. Concretely, in the reported case: `.bg-black\/40` sorts after `.bg-transparent` ("black" > "transparent" alphabetically), `.text-white` sorts after `.text-black\/30` ("white" > "black"), and `.hover\:bg-black\/60` sorts after `.hover\:bg-black\/20` (60 > 20 numerically) - so the *built-in* class won every one of those three, regardless of the user's intent, while `w-40` only "worked" by the exact same coincidence running the other way (40 > 8). Nothing about the class names themselves predicts which side Tailwind will pick.

**Fixed at the root, not patched around**: `navClass`/`arrowClass`/`homeClass`/`tabClass`/`activeTabClass` (`itemClass`/`activeItemClass` renamed and split by role) are no longer appended alongside hardcoded defaults - each field IS the complete class list for that part, with its default value (`ElementsClass.js`'s `Slider()` builder) set to the exact classes that part used to have hardcoded. Components apply ONLY the field's current value (plus a small, disjoint set of positioning classes - `absolute`/`top`/`left`/`right`/`bottom`/`-translate-*` - that never share a CSS property with anything a custom class would set, so there's nothing left for them to conflict with). `SliderTabsNav.vue`'s active-vs-inactive tab styling was the same bug in miniature (`activeItemClass` layered over `itemClass`, same-element, same-property collision) - fixed by giving each tab EITHER `tabClass` OR `activeTabClass`, never both together. `FloatingToolbar.vue`'s text inputs now show each field's real current value (pre-filled from the default, not an empty box with a placeholder example) - what you see is genuinely the whole class list in effect, editable in place.

Verified directly against the real engine both ways: compiled the OLD (concatenated) class list and confirmed the built-in `bg-black/40`/`hover:bg-black/60`/`text-white` rules generate *after* their custom counterparts in the stylesheet (i.e. would win, reproducing the exact reported symptom); compiled the NEW (single-field) class list and confirmed the custom classes are the only rules present for those properties at all, with nothing left to lose to.
