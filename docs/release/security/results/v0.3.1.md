Counts, read from the reports of run 40297447238 (commit `99365c4`): API suites **2337 passed, 0 failed, 2 skipped** (92 test files); browser tests **56 passed, 0 failed,
5 skipped**; isolation **14 passed, 0 failed**. The reports are attached to the GitHub Release (`security-reports-v0.3.1.zip`), with the CycloneDX SBOMs of the source and of the
six images.

The static report lists, as warnings that do not fail the run, the same four semgrep hits as in 0.3.0 (three `bypass-tls-verification` in
`packages/core/src/db/client.test.ts`, one `react-dangerouslysetinnerhtml` in `packages/sdk/react/src/defaults.tsx`), still not in the baseline. Moderate and low advisories are
listed as information: `@tiptap/core`, `katex`, `postcss-selector-parser`, `sanitize-html` (as in 0.3.0) and, new since 0.3.0, `nodemailer` (three, address parsing) and `fast-uri`
(four). None is high or critical; they are not fixed in this release.

**Image scan** (`trivy image`, HIGH/CRITICAL, fixed only), run 40297447238: five own images (`core-api`, `asset-processor`, `gateway`, `admin-dashboard`, `whoobe-one-spike`) and `garage` **0**; the sixth, `publisher`, is **not in the scan** (see below and F-063); `postgres:16-alpine` 26, all in the Go standard library of `gosu`
(reported, not gating, decision of the owner 2026-10-23; F-050).

**The published images.** After the release run, the six images on `ghcr.io` were checked by digest (the digests are in the release notes of the GitHub Release):

- the cosign signature of each image (keyless, identity `https://github.com/swina/whoobe_project/.github/workflows/release.yml@refs/tags/v0.3.1`, issuer
  `https://token.actions.githubusercontent.com`): **verified, 6 of 6**;
- the SLSA build provenance stored with each image (`cosign verify-attestation --new-bundle-format --type slsaprovenance1`, same workflow and tag): **verified, 6 of 6**;
- `trivy image` 0.58.1 (HIGH/CRITICAL, fixed only) on the published digests, amd64: **0** for `core-api`, `asset-processor`, `gateway`, `admin-dashboard` and
  `whoobe-one-spike`; **171 (11 critical) for `publisher`**.

The `publisher` image was never in the CI image scan: `run-trivy-image.sh` lists the images with `docker compose config --images`, and the publisher sits behind the
compose profile `publisher`. This is a gap of the test, found after the tag, and the same holds for every earlier release record. The 171 are almost all in build
tools shipped with the image: the Go standard library of three `esbuild` binaries (115), `pnpm` 9.0.0 left by corepack in `/root/.cache` and the `npm` of the node base
image (about 40), and dev and build packages of the app's tree (`vite` 5.4.21 and 6.4.3, `vitest` 1.6.1, `tinypool`, `devalue` 5.9.0, `brace-expansion`). The publisher
is optional (compose profile), publishes no port and runs these tools only for the site builds the dashboard asks for. Recorded as **F-063** (Medium, open); the fix
(scan the profile images in CI, slim the image) goes into a later patch.

The SBOMs of the six images attached to the release were generated by `trivy` from the published digests.

## What this run did not cover

The list of [v0.3.0](v0.3.0.md#what-this-run-did-not-cover) still holds; nothing of it was done for this patch. For this release in particular:

- the `publisher` image (above, F-063);

- the move to **Zod 4** was checked by the unit and API suites only: a manual try of the site wizard, the import of a site specification and writes through the gateway on a
  running stack was not done (release notes, "Known limits");

  not a review of each package.
