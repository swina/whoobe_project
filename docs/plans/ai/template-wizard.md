# Plan: template wizard, a site from a few choices

Status: **phases 1 and 2 done** (engine; routes and tab, 2026-10-20); phases 3 and 4 proposed. It builds on `ai-site-spec.md` (phases 1 and 2 are
done on branch `feat/ai-site-spec`) and replaces that plan's phase 3.

## 1. Why

The site specification is a JSON file. That is right for a developer and for a language model, and wrong for the people who make
sites: many designers and editors do not know what JSON is, and an installation on a LAN may give them no tools but the dashboard.
The window "Import from a spec" works, but "copy these instructions to a model and paste its answer back" is still a process only
a technical person enjoys.

What an editor does know is the way the editor itself works: a page is a stack of **blocks** with names everybody uses (header, hero,
banner, call to action, box grid, form). The AI Snippets already generate such blocks one at a time. This plan lets a person choose
the blocks of a whole site from a guided form, and gets the site from them.

## 2. Goal and non-goals

Goal: a person with only the dashboard answers a few questions (what kind of site, which pages, which blocks in each, the look,
the sector) and gets a **draft website** that looks consistent, reads sensibly for the sector and is ready to be edited.

Not goals: a design tool; a perfect result without editing; a replacement for the editor; connecting the form to anything; publishing.
The result is a starting point that a person reads and improves, as with the spec import.

## 3. What the person sees

```
Generate Website Wizard   (a tab of the dashboard, opened from the Websites card: a form of several steps is too big for a window)
  1 Basics      name, language (one), sector (IT, Food, Consultant, Insurance, Tourism), market context (free text: "Hotel", "Bakery"...)
  2 Look        theme  [Dark] [Light] [Light colours] [Blue navy] [Company colour: a background, e.g. #323932]  + an accent colour (optional)
                fonts  [Sans-serif] [Serif]
  3 Pages       Landing page + up to 3 inner pages; for each: title, and its structure
                  Structure = an ordered list of blocks
                    [Hero] [Banner] [CTA] [Box grid 3] [Box grid 6] [Form]   (add, remove, reorder)
                  at any position: "a generated block" or "an existing snippet of my library" (filtered by the same category)
  4 Navigation  header and footer, made from the pages chosen (nothing to type)
  5 Texts       [Placeholder texts]  [Write the texts with AI]   (the second only when an AI provider is configured and the person may use it;
                with it: a line or two about the business, which the model may use)
  6 Check       what will be created (pages, blocks, snippets, theme), conflicts with names that exist, name and root path
  7 Create      a draft website opens in the editor
```

Every step has a sensible default, so the shortest path is: name, sector, press *Create*. The sector proposes a structure (a hotel
landing page opens with a hero, a box grid of rooms and services, a banner, a CTA, a contact form) that the person can change.

## 3.1 The blocks (version 1)

Names are the category names snippets already use, so a generated block and an existing snippet are interchangeable at the same place.

| Block | What it is | Content it takes |
|---|---|---|
| `header` | brand and navigation links, optional button | made from the pages |
| `footer` | brand, links, a short line | made from the pages |
| `hero` | the opening of a page: heading, lead, one or two buttons, an image placeholder | title, lead, button texts and targets |
| `banner` | a narrow band with one message and one link | message, link |
| `cta` | a closing call to action: heading, a line, a button | title, line, button |
| `box-grid-3` | three boxes (title and text each) | heading, three items |
| `box-grid-6` | six boxes in two rows | heading, six items |
| `form` | a **contact form template**: fields and a submit button | field labels, button text |

Each block exists in the four themes and both font families. More blocks and variants (testimonials, pricing, FAQ, gallery) are a later phase.

## 4. Decisions

**D1. The wizard composes a site specification; the engine is the one already built.** The answers become a `SiteSpec`
(`packages/sdk/schema`), which goes through the same validation, expansion, dry run, choices about existing items and import as a spec
written by a model (`importSiteSpec`). The specification window stays where it is, for developers and for people who use an
outside model. One writer to the database, one set of checks.

**D2. Structure is generated by fixed templates, not by a model.** A block is a function (answers in, spec elements out), so the same
answers give the same site, it works without any AI configured, in the public sandbox and on an isolated LAN, and it cannot surprise
anybody. A model is used, if at all, only for the words (D6).

**D3. Blocks and snippets share names; a position takes either.** A position in a page structure is either a generated block of a
category or a snippet of the library of that category (`{ kind: "snippet", use }` in the spec, which already exists). A generated block can
also be saved as a snippet, so it joins the library and the next site can use it.

**D4. Theme: four presets, or a company colour.** *Dark*, *Light*, *Light colours* and *Blue navy* each fix the colour roles (page, section,
text, muted text, accent, accent text, border), written once as Tailwind classes plus the colours of the theme object. The free input is a
**company colour**: the **background** of the site (`#RRGGBB`, a colour picker or typed, for example `#323932`). From it the wizard derives
every other role: the text is white or near-black, whichever reads better on that background; the muted text, the border and the alternate
sections are shades of the background; the accent is the one of the nearest preset unless the person gives an **accent colour** too, and the
text of an accent button is again white or near-black. Black or white always reaches at least 4.5:1 on any background, so a derived palette
can always be readable. A test computes the contrast of every text/background pair of every preset **and of a spread of company colours**
(every hue and lightness step, including the greys in the middle) and fails under WCAG AA (4.5:1 for text, 3:1 for the accent against its
background), so neither a preset nor a colour a person types can produce an unreadable site. A free-text description of the look ("warm,
like a bakery") needs a model and is not part of version 1.

**D5. Fonts: sans-serif or serif, no outside request.** The two choices use the system font stacks (Tailwind's `font-sans` and `font-serif`
classes), so a page makes no request to a font service: it works on a LAN with no outbound access and sends nothing anywhere. Web fonts can
be added later as an explicit option.

**D6. Sector and market context decide the words; the person chooses where the words come from: placeholder texts or the configured AI.**
- **Placeholder texts.** Version 1 ships written copy for each block, in the language of the site, for each of the five sectors, and the market context
  (for example *Tourism > Hotel*) fills the noun the copy uses ("your hotel", "our rooms"). The copy is plain and generic by design, and the
  window says so: it is there to be replaced.
- **Write the texts with AI.** The choice is a step of the wizard, shown only when an AI provider is configured and the person may use it. It sends the sector, the context,
  the site name and a short description, and gets back only the **texts of the slots** (titles, leads, box texts, button labels). The reply is
  validated slot by slot, cleaned like every rich text and cut to the length of the slot; it cannot change structure, classes, links or
  anything else. It uses the existing AI settings and rate limit, is off in the sandbox like the rest of `/ai/`, and a person reads the
  result before the site is created. We make no claim about the quality of what a model writes.
- Sectors are a list the installation can extend later; the five of the first version are IT, Food, Consultant, Insurance, Tourism. The **market
  context is free text** ("Hotel", "Bakery", "Insurance broker"): it is cleaned and cut to a few words, fills the noun of the placeholder copy and
  goes to the model when the AI writes the texts. There is no list of contexts to keep.
- **Placeholder copy is English in the first version.** The AI writes in the language of the site; more placeholder languages come with phase 4.

**D7. Pages: a landing page and up to three inner pages, in one language.** The limit is the generator's, as for the AI wizard. Each page has a
title (the sector suggests *About*, *Services*, *Contact*...) and its own structure. The first page is the home page (`/`); the others get a slug
made from the title.

**D7b. One language in the first version; two later.** Two languages double the copy to write and to check, the header and the footer and the
choices of the wizard, and the engine supports them already (the specification takes one or two). The wizard asks for **one** language; the
placeholder texts exist for the languages we write (English first, D6) and the AI writes in any. Two languages are a later phase (phase 4).

**D8. Header and footer come from the pages.** The header lists the pages in order, the footer repeats them with the name and a line. With one
language the layout of the specification as it is today is enough. When two languages come (phase 4) the spec will be extended (version 1.1) so that
`layout` can be given **per locale** (the website template model already has a `locale`), because a layout shared by two languages cannot carry
link texts in both.

**D9. The form block is a template of fields, not an integration.** A contact form with its fields (name, email, message by default; a field is
a label, a type of text, email, phone or long text, and a required flag) and a submit button. It is created **disconnected**: no target class, no
endpoint, no address to send to, no notification (`formConfig.enabled` false). A developer, who is not the person making the site, connects it
later in the editor to a data class, a gateway endpoint or an automation. The spec gets a `form` kind for this purpose, and **has no key for an
action, a target or a recipient**, so a specification cannot make a form post anywhere. The dashboard says, next to the block, that the form is
not connected.

**D10. The result is the same as for a spec import:** a draft, names that exist are the person's choice (reuse or create a new one, nothing
existing is changed), the root path is checked, and the creation is audited. Permission: the same as the import (`websites:create` or
`objects:write`).

**D11. The wizard is a tab, and replaces nothing that exists.** It is the button **Generate Website Wizard** of the Websites card, opening a tab (a
view of its own, like Publish), not a window. The old AI Website Wizard (hidden behind a commented button) and the specification window
(*Import from a spec*) stay where they are; whether to hide them is decided once the wizard is in use.

## 5. Delivery in phases

Each phase is its own branch, with `CHANGES.md`, tests and a "done" criterion, and does not depend on the later ones.

**Phase 1: engine (no screens).**
- Spec: the `form` kind (D9) with its rules and failing examples; expansion of `form` into a disconnected Form element with its inputs (names,
  types, required), checked by test to carry no target and no action.
- `packages/core/src/site-wizard/` (pure): the answers schema (`WizardAnswers`, Zod, strict), the block functions, the theme presets, the
  font choices, the placeholder copy for the five sectors, and `wizardToSiteSpec(answers) -> SiteSpec`. The copy takes slots by name, so the
  texts of phase 3 fill the same slots.
- Done when: every block validates; a **matrix test** expands every combination of sector, theme, font and language into a spec that
  `validateSiteSpec` accepts and `expandSiteSpec` turns into a bundle that imports on an empty database; the contrast test passes for every preset;
  the same answers give the same spec; a page has one `h1`; every image has an alt text; every link has text and a target.

**Phase 1 delivered (2026-10-20, branch `feat/ai-site-spec`).** `packages/core/src/site-wizard/` (answers schema, blocks, palettes, copy, slots,
`wizardToSiteSpec`) and the `form` kind of the specification. The matrix test runs 140 combinations of sector, theme, font and structure through validation,
expansion and parsing, and three integration tests import wizard sites on a disposable database. What it showed:
- **Two mistakes of mine, found by the contrast test:** near-black text (`#0B0F14`) falls to 4.38:1 on the middle greys, so pure black is used there; and
  a mid-green background (`#66804D`) took white text that neither white nor near-black could make readable. Both fixed; the test now covers 2 600+
  combinations of background and accent.
- **The text slots keep the structure fixed:** other words for the same keys change only text (tested by emptying every text field and comparing).
- **Seen, not only tested:** three generated sites (tourism on navy, food on light colours with serif, IT on the company colour `#323932`) were imported on
  the throwaway stack and looked at in the editor: header, hero, boxes, banner, CTA, form and footer read well in all three. Looking found what the tests did not:
  the hero of an inner page repeated the welcome line of the home page and had a button leading back to the same page. An inner page hero now has its title and a
  plain line, and no buttons (a test covers it).
- **A limit to say out loud:** the placeholder copy is written per sector and the market context only changes a noun, so a "bakery" under Food reads like a
  restaurant ("a table waiting for you"). That is what placeholder copy is; the AI texts (phase 3) are the answer, and the wizard says that the texts are to be replaced.
- Not in this phase, as planned: the route, the dashboard tab, the choice of the source of the texts, the AI, a second language.

**Phase 2: route and dashboard.**
- `GET /whoobe-one/site-wizard/options` (sectors, contexts, blocks, themes, fonts, the snippets of the library by category) and
  `POST /whoobe-one/websites/from-wizard` (`?dryRun=1`) which turns the answers into a spec and calls `importSiteSpec`; both in the API
  reference, `routes.expected.json` and the audit log.
- The stepper of section 3 as a tab of the dashboard (button *Generate Website Wizard* in the Websites card), a schematic preview of each page (boxes
  with the block names), the check step of the spec import reused. The specification window and the old AI Website Wizard are not touched.
- Done when: a browser test goes from the empty form to a draft website with the chosen pages and blocks, with only a browser; the same with a
  library snippet in one position; the form block says it is not connected; the access of the routes is checked by the authorization matrix.

**Phase 2 delivered (2026-10-20, branch `feat/ai-site-spec`).** The routes `GET /whoobe-one/site-wizard/options` and `POST /whoobe-one/websites/from-wizard`, and the
tab **Generate Website Wizard** (Basics, Look, Pages, Texts, Check and create) with a schematic preview of the pages. The browser test goes through every step, uses a library
snippet in a position, checks that the contact form is stored not connected, and meets the names that exist on a second run. Notes: the Navigation step of the plan is
part of the Pages step (the header button and the order of the pages), because it has nothing to type; the specification window and the old AI Website Wizard are untouched;
the step *Texts* shows the AI as not available, to be switched on by phase 3. Per the maintainer's decision the branch is merged after this phase.

**Phase 3: the texts with AI.** (The step *Texts* is in the stepper from phase 2, with the AI choice switched off until this phase lands.)
- `POST /ai/generate-wizard-texts` (slots in, texts out; validated, cleaned, length-limited), the choice of the step *Texts*, offered only when an
  AI provider is configured. Tested with a mock provider: a reply that tries to add markup, links, a script or a key that is not a slot is refused or cut.
- Done when: the structure of the site is identical with and without the texts, and only slot texts differ.

**Phase 4: two languages, then more.** A second language: the wizard asks for it, pages and texts are written once per language, the spec gets
`layout` per locale (version 1.1), the matrix test covers it. Then more blocks and variants, more sectors and contexts, web fonts as an option, kits as a source of blocks (the kit library already
ships and versions collections of templates), a free-text look description with a model.

## 6. Tests and checks

- Unit: every block and every preset; the answers schema (a strict object, limits, defaults); determinism.
- Matrix: sector x theme x font x languages through validation, expansion and import (disposable database).
- Accessibility basics as tests: contrast of every preset (WCAG AA), one `h1` per page, alt text on images, link text.
- Security: the answers are untrusted input like a spec (they go through the same schema, so classes, links and text are checked and cleaned); a
  form cannot carry a target; the routes need the permission; a reply of a model (phase 3) cannot change anything but slot texts.
- Browser: the whole path of phase 2, with and without a library snippet; in phase 4 also two languages.

## 7. Risks and what we do not claim

- **Sameness.** Fixed templates give sites that look alike. That is the price of reliability; the editor is where a site becomes its own.
  We do not claim designs, and we say in the wizard that the result is a starting point.
- **Placeholder copy is generic.** It is there to be replaced. Writing it well, for five sectors, is real work and its quality is checked by a
  person before release, not by a test. A person who wants real words can choose the AI (D6), and the same warning applies to what it writes.
- **Maintenance of the library.** Every block exists in four themes and two font families; a matrix test and the contrast test keep that honest, but
  adding a block costs more than one function.
- **Scope.** The list of blocks, sectors and themes will want to grow. Each addition is a phase with tests, not an edit.
- Nothing about "works with any model" or about the quality of generated words is claimed anywhere until it is measured and published with the
  model, the prompts and the failures.

## 8. Decisions taken by the maintainer (2026-10-20)

- Market context: **free text**, not a list (D6).
- Placeholder copy: **English** in the first version (D6); the AI writes in the language of the site.
- Theme: the free input is a **company colour** used as the background, e.g. `#323932`; the other roles are derived and checked for contrast (D4).
- Place: **Generate Website Wizard**, a **tab** opened from the Websites card; the old AI Website Wizard and the specification window stay where
  they are for now (D11).
- Branch: `feat/ai-site-spec` is merged **after phase 2 of this plan**.
- One language in the first version, two in phase 4 (D7b); the choice of the source of the texts, placeholders or the configured AI, is a step of the wizard (D6).

No question remains open; the next step is to approve the plan and start phase 1.
