# Porting `whoobe-one-studio` (Vue 2) to Vue 3

## 0. Why this repo, and how it differs from what's already in this codebase

The user identified `https://github.com/swina/whoobe-one-studio` (their own repo, full control) as the *real* editor to build on - distinct from `whoobe-studio-alpha-01`, which was evaluated earlier this session and partially cherry-picked (`apps/whoobe-studio/src/ported/`, see `pimcore-areablock-import-plan.md` §"Whoobe Studio Alpha... evaluated, partially adopted"). The two repos are not the same codebase at different ages - they're genuinely different apps:

| | `whoobe-studio-alpha-01` (already evaluated) | `whoobe-one-studio` (this plan) |
|---|---|---|
| Editing model | Tree + JSON-form field editor (not truly WYSIWYG - this was the user's original complaint that started this session's Tailwind-conversion work) | **Real inline editing**: elements are rendered as actual live HTML with `contenteditable` set directly on the rendered tag; click an element, its content becomes editable in place, blur syncs it back to state. No JSON form for content editing at all. |
| Reordering | None built | **Native drag-and-drop** via `dragula` directly on the rendered container tree - drag any element into any container. |
| Backend coupling | FeathersJS services + Socket.io wired into component lifecycle hooks throughout (`this.$api.service(...)`, `.on('created', ...)`) - the actual reason it was rejected for full adoption | **None.** Confirmed: `socket.io-client` is a dependency but is used nowhere except as placeholder example text in an unrelated, orphaned NPM-lookup dev tool (`Package.vue`). All persistence is local: Dexie (IndexedDB) for the templates/pages library, plain JSON import/export for portability. |
| Data model per node | Whatever FeathersJS "components" schema dictated | A dedicated `Element` class (`src/scripts/ElementsClass.js`) with rich per-node state: Tailwind class strings (`css.css`/`css.container`), inline `style`, GSAP animation config, AlpineJS directive map, per-node custom events, link/anchor, image, form-input metadata - built via a fluent builder (`new Element().Heading(1).setIcon(...)`). |
| Maintenance state | Abandoned, Vue 2/EOL | Also abandoned (last commit 2021-12-09, README says "still in alpha version"), also Vue 2/EOL - **not more actively maintained**, just architecturally closer to what "WYSIWYG editor of editables" actually means. |

Net: this is a materially more complete, more real inline visual builder than anything evaluated or built so far in this project. It is not, however, less stale - it's frozen at the same Vue 2/Tailwind-v1-v2-era snapshot as everything else evaluated this session, and needs the same category of porting work.

## 1. Architecture inventory

### 1.1 Core data model (`src/scripts/`) - the "elements definitions" the user pointed at

- **`ElementsClass.js`** (541 lines) - `class Element`, a fluent builder for one node. Every element type is a method (`.Grid()`, `.Flexbox(options)`, `.Heading(level)`, `.Paragraph()`, `.Image()`, `.Slider()`, `.Video()`, `.YTVideo()`, `.VimeoVideo()`, `.Icon()`, `.Iconify()`, `.Download()`, `.Form()`, `.InputText()`/`.InputEmail()`/`.InputNumber()`/`.InputCheckbox()`/`.InputTextarea()`/`.InputSelect()`/`.InputSubmit()`/`.InputReset()`, `.Button()`) that mutates `this` and returns `this`. `.Groups()` returns the static palette shown in the "add element" sidebar (containers/text/media/form), and `.createElement(name, options)` is the dispatcher the palette UI calls. Every node carries: `id`, `blocks` (children array), `css.{css,container}` (Tailwind utility strings), `tailwind` (structured per-attribute state used by the customizer UI), `font`, `style`, `content`, `alpine` (directive map), `events` (display/hide/mouseenter/mouseleave/click/focus/blur/keydown), `data` (type-specific extras - `options` for selects, `icon` for iconify, `attributes` for form inputs), `gsap` (animation/ease/duration/delay), `link`/`anchor`, `image.url`, `type`, `tag`, `editable` (drives whether `contenteditable` is set), `icon`, `helper` (path to a setup-wizard component like `Grid.vue`), `dialog` (a Tailwind width class for that wizard's dialog).
- **`BlocksClass.js`** (75 lines) - `class Block`, one whole saved document/component: `id`, `blocks_id` (random), `name`, `description`, `category`, `tags`, `json.blocks` (the root `Element` tree), `json.build` (computed at export time: `purgeCSS()`/`purgeImages()`/`fonts()`, each walking the tree via `jsonpath` queries to collect everything needed for a purged static build).
- **`templates.js`** (358 lines) - `class Template`, ~18 snippet-builder methods (`navbar()`, `cta()`, `hero()`, `article()`, `pricing()`, `slider()`, etc.), each just chaining `Element`/`Block` builders. Confirmed 100% plain-JS data construction, zero rendering code - portable unchanged.
- **`tw.classes.js`** (606 lines) / **`tw.groups.js`** (138 lines) - static Tailwind utility-class lookup tables and the customizer panel's group→control→attribute config, consumed by `BlockTailwind.vue` and the 14 `tailwind/controls/*.vue` atoms. Pure data, zero Vue code - but see the version-mismatch risk in §4.
- **`grid.js`** (9 lines), **`animations.js`** (495 lines, pure `gsap.registerEffect()` config data) - pure data, portable unchanged.
- **`editor.js`** (311 lines), **`database.js`** (186 lines), **`index.js`** (48 lines), **`gsap.js`** (93 lines) - these four are **Vue 2 plugins** (`export default { install(Vue){ Vue.prototype.$x = ... } }`), the mechanism that hangs ~30 global instance methods off every component (`$clone`, `$removeNode`, `$duplicateBlock`, `$exportDocument`, `$beautify`, `$icons`, `$purgeCSS`, `$savePage`, `$importDB`, `$animation`, `$eventBus`, etc.). This is the single biggest mechanical porting task - see §3.
- **`DatabaseClass.js`** (118 lines) - `class Database extends Dexie`, plain IndexedDB wrapper (pages/settings tables). Zero Vue coupling, portable unchanged.
- **`hotkeys.js`** (192 lines) - one `window.addEventListener('keydown', ...)` dispatching editor actions via the event buses based on `Alt+<key>` combos. Vanilla DOM APIs only, portable unchanged (the event-bus calls inside it need the same swap as everything else, see §3).

### 1.2 Core editing UI (`src/components/blocks/`)

- **`BlockEditor.vue`** (342 lines) - the editor shell/root. Mounts `BlockContainer` for the live document, plus floating toolbar components (`BlockFloatingAction`, `BlockFloating`) positioned via manually-tracked `getBoundingClientRect()` coordinates. Owns autosave (`setInterval` calling `$savePage()`), and registers ~10 `editorBus.$on(...)` handlers in `mounted()` (`floatingElement`, `editorAction`, `importComponent`, `selectedMedia`, `setFlexRow`/`setFlexCol`, `copyBlockCSS`/`pasteBlockCSS`, etc.).
- **`BlockContainer.vue`** (183 lines) - recursive container renderer. Reads its data via **`this.$attrs.doc`/`this.$attrs.level`, not declared props** (confirmed pervasive pattern - see §3). Registers a `dragula` instance in `mounted()` for drag-and-drop reordering/re-parenting across the whole tree, with `accepts`/`move` predicates checking `type==='element'` vs `'container'`. Dispatches to `Slider`/`BlockElement`/`BlockIFrame`/`IconifyIcon` per child based on `block.type`/`block.tag`.
- **`BlockElement.vue`** (154 lines) - the leaf-node renderer, and **the actual inline-editing mechanism**: `<component :is="component" :contenteditable="element.editable" v-html="element.content" @blur="handleInput" @click="setCurrent(element)">`. `handleInput()` reads `e.target.innerHTML` on blur and writes it back into the reactive `element.content`. This is genuinely simple and framework-agnostic - the "WYSIWYG" claim is earned by this one binding, not by any editor library.
- **`BlockElements.vue`** (73 lines) - the "add element" sidebar palette, iterates `Element.Groups()`.
- **`components/BlockTipTap.vue`** (137 lines) - a richer rich-text mode for paragraphs, using `@tiptap/vue-2` + `@tiptap/starter-kit` + `@tiptap/extension-image`. Only reachable for `element === 'p'` nodes (triggered from `BlockEditContent.vue`'s `mounted()` via `$dialogBus('TipTapEditor')`) - most text nodes just use the plain `contenteditable` path above; TipTap is the exception for paragraph-level rich formatting (bold/italic/headings/lists/blockquote/image-in-text).
- **`components/BlockEditContent.vue`** (43 lines) - the floating "edit content" panel body (plain textarea, or TipTap for `<p>`).
- **`tailwind/BlockTailwind.vue`** (146 lines) + **`tailwind/controls/*.vue`** (14 small atoms, e.g. `tailwind.color.vue`, `tailwind.range.vue`, `tailwind.bg.gradient.vue`) - the "customize any TailwindCSS utility" panel. Dynamically resolves which control components to show per `tw.groups.js` group config, writes results back into `element.css.css`.
- **`components/BlockAlpine.vue`**, **`BlockAnimation.vue`**, **`BlockEvents.vue`**, **`BlockAttributes.vue`**, **`BlockCss.vue`**, **`BlockFont.vue`**, **`BlockTextColor.vue`**, **`BlockLink.vue`**, **`BlockForm.vue`**, **`BlockSelect.vue`**, **`BlockHtml.vue`**, **`BlockIconFinder.vue`**, **`BlockImageUrl.vue`**, **`BlockAddToUIKit.vue`**, **`BlockLibrary.vue`**, **`BlockJSEditor.vue`**, **`BlockShortcuts.vue`**, **`BlockContextMenu.vue`**, **`BlockFloating*.vue`**, **`BlockTree.vue`** - the remaining per-node control panels (AlpineJS directives, GSAP animation picker, custom events, HTML attributes, semantic/CSS editor, font picker, text/background color, link/anchor, form settings, HTML dialog, icon search, image-URL import, add-to-UI-kit, snippet library browser, custom-JS editor, keyboard-shortcut help, right-click context menu, floating toolbar chrome, DOM tree view). All small (8-96 lines), all follow the same `$attrs`-not-props and event-bus patterns already described.

### 1.3 A second, parallel, read-only rendering tree (`src/components/blocks/preview/`)

**Confirmed via the Explore survey: this is a genuinely separate, duplicated implementation, not a shared one.** `preview/BlockContainer.vue` and `preview/BlockElement.vue` re-implement container/element rendering from scratch (same CSS-joining/style-building logic, no `contenteditable`, no `dragula`, no `setCurrent`/selection) with their own isolated import graph rooted at `preview/`. This is what renders inside the "realtime preview (laptop/tablet/smartphone)" feature, via `BlockWindowPreview.vue` (363 lines), which does two structurally different things depending on mode:

- **Fullscreen preview**: mounts the preview tree live, in-document, inside a `laptop-view` wrapper - real reactive Vue rendering.
- **Tablet/smartphone preview**: scrapes `document.getElementById('content').outerHTML` from the already-rendered fullscreen tree, wraps it in a hand-built static HTML string with hardcoded CDN `<link>/<script>` tags (Tailwind CDN, Google Fonts, Material Icons, Alpine.js), beautifies it, and assigns it to an `<iframe :srcdoc="...">`. This is a static snapshot, not a live/reactive preview - it has to be regenerated wholesale on every edit, not incrementally updated.

This duplication (editable tree + preview tree, ~250 combined lines of near-identical container/element logic) is itself a candidate for consolidation during the port, not just a straight copy-paste port - see §5.

### 1.4 State (`src/store/`) - flat Vuex, mechanically simple

`store/index.js` wires five modules: `editor` (current document/page/selection/settings state), `datastore` (misc app-level lookups, partially vestigial), `desktop` (open tabs, sidebar state), `user` (near-empty), `generator` (near-empty, unused). **Confirmed via the Explore survey: every module across all five is a flat one-mutation-per-key, one-action-per-mutation pattern with no cross-module `rootState` access, no async actions, and (with one exception) no side effects inside mutations.** The one exception: `desktop.js`'s `currentTab` mutation writes directly to `localStorage` as a side effect - a pre-existing anti-pattern, not Vue3-specific, worth cleaning up rather than preserving during the port.

### 1.5 Dialog/event-bus system (`src/main.js`, `src/components/dialog/`)

Five separate `new Vue()` instances constructed purely as event emitters and exported from `main.js`: `eventBus`, `dialogBus`, `modalBus`, `editorBus`, `errorBus`. `dialog/Dialog.vue` (312 lines) and `dialog/Modal.vue` (78 lines) are central routers: each registers ~25 / ~5 `xBus.$on('name', () => { this.component = () => import(...) })` handlers respectively, so every dialog/modal in the app is opened by emitting a named event on the right bus rather than through component props or a router. This is the second-biggest mechanical porting task after the `Vue.prototype.$x` plugins - see §3.

## 2. Vue 2 → Vue 3 breaking-change inventory (scoped to what's actually in this codebase, not generic migration-guide advice)

Confirmed by direct reading (core files) plus a targeted Explore survey (all ~57 remaining `.vue` files, all remaining store modules/scripts, `router/index.js`) - every pattern below was grepped for across the whole `src/` tree, not assumed.

| # | Issue | Where | Fix | Effort |
|---|---|---|---|---|
| 1 | **Five `new Vue()` event buses.** Vue 3 app instances (`createApp()`) have no `$on`/`$off`/`$emit` at all - not deprecated, removed. | `main.js` (construction) + pervasive `.$on()`/`.$emit()` calls throughout nearly every component and script (dozens of named events: `notification`, `loading`, `editorAction`, `floatingElement`, `linkBlock`, `dbImported`, etc.) | Swap each bus for an [`mitt`](https://github.com/developit/mitt) instance - `mitt()` has the same `.on(type, cb)`/`.off(type, cb)`/`.emit(type, payload)` shape, so every call site is a mechanical `$on`→`on`/`$emit`→`emit` rename, not a redesign. (Pinia-action-based pub/sub is the other official option but is a much bigger rewrite for no real benefit here, given how many independent named events exist.) | **High mechanical volume, low design risk** - this is the single largest line-count porting task, but it's find-and-replace, not re-architecture. |
| 2 | **~30 `Vue.prototype.$x` global instance methods**, across `scripts/index.js`, `scripts/editor.js`, `scripts/database.js`, `scripts/gsap.js`, plus one-offs in a couple of components. Vue 3 still supports `app.config.globalProperties.$x` as a direct equivalent (not removed), but it's discouraged in favor of composables/`provide`-`inject`, and some of these methods (`$router`-adjacent, store-reading ones) are easiest to convert to `use*()` composables anyway once touching the file. | `scripts/index.js`, `editor.js`, `database.js`, `gsap.js`; consumed by nearly every `.vue` file | Two viable strategies: (a) mechanical - register the same methods via `app.config.globalProperties` in the new `main.ts`, zero call-site changes; (b) cleaner - wrap each plugin's methods as a `useXxx()` composable and update call sites from `this.$x(...)` to `const { x } = useXxx(); x(...)`. Given the call-site volume, recommend (a) as the *port*, with (b) as an optional later cleanup once the port is proven working - don't conflate the two. | **Medium** - contained to 4 source files even though call sites are everywhere, since (a) requires zero call-site changes. |
| 3 | **`this.$attrs.xxx` used in place of declared `props`**, confirmed pervasive: `BlockElement.vue`, `BlockContainer.vue`, `preview/BlockContainer.vue` (27 `$attrs` reads, the heaviest single file), `preview/BlockElement.vue`, `preview/BlockSlider.vue` (16), `PackageTree.vue` (7), and roughly 40 of the ~57 files surveyed in `common/`/`dialog/`/`media/`/`gallery/`/`helpers/`/`tailwind/controls/`. This mostly still "works" in Vue 3 (undeclared attrs still land in `$attrs`), but two real semantic changes will bite: (a) Vue 3 merges `class`/`style`/`v-on` listeners **into** `$attrs` (previously separate `$listeners` in Vue 2) - any code that iterates `$attrs` wholesale (none found doing this yet, but worth re-checking per-component during the port) could pick up unexpected keys; (b) **writing to `$attrs`** (confirmed at `common/block.image.placeholder.vue:41`, `this.$attrs.image = image`) does not propagate the way Vue 2 sometimes tolerated - `$attrs` in Vue 3 is not a reliable write target. | ~40 files, concentrated in `common/`, `dialog/`, `media/`, `blocks/preview/`, `tailwind/controls/` | Convert to declared `props` during each file's port pass (not a bulk find-replace - each file's actual attrs need enumerating). The `$attrs.image = image` write-site specifically needs to become a proper `emit('update:image', image)` + parent `v-model`/`@update:image`. | **Medium-high**, but embarrassingly parallel (file-by-file, no cross-file dependencies) - good candidate to split across multiple work sessions or even multiple people/agents. |
| 4 | **`slot="xxx"` attribute-on-child syntax** (Vue 2 named-slot shorthand, fully removed in Vue 3 - not deprecated-but-working, an actual template compile error). Confirmed **live** (not commented out) at `media/Media.vue:23-24` against `common/Modal.vue`'s `<slot name="title">`/`<slot name="body">`. A second occurrence in `media/pixabay.vue:53-82` is confirmed dead/commented code, no fix needed. | `media/Media.vue` (2 lines) | `<template #title>...</template>` / `<template #body>...</template>` | **Trivial**, 2 lines, but must not be missed since it's a hard compile error, not a soft warning. |
| 5 | **`router/index.js`**: `mode: 'history'` → `history: createWebHistory(...)`; `new VueRouter({...})` → `createRouter({...})`; `Vue.use(VueRouter)` removed entirely (router is `app.use(router)` instead). Also a `VueRouter.prototype.push` monkey-patch (lines 15-18, swallowing `NavigationDuplicated`) that won't work post-port since `VueRouter` becomes a factory function with no prototype to patch the same way. | `router/index.js` (52 lines total, only one real route - everything else is already commented out) | Standard Vue Router 4 API swap; replace the prototype patch with a wrapper around the router instance's own `.push()`. Vue Router 4 already resolves/no-ops duplicate navigations more gracefully by default, so the wrapper may end up unnecessary - confirm during the port rather than assuming. | **Trivial** - smallest file in the whole app, and most of it is already dead/commented. |
| 6 | **`this.$set`/`this.$delete`** (Vue 2 reactivity-caveat workarounds, unnecessary in Vue 3's Proxy-based reactivity - not broken, just vestigial). Confirmed only 2 call sites app-wide (`App.vue`, `desktop/Settings.vue`). | 2 files | Delete the `$set`/`$delete` wrapper, do plain property assignment. | **Trivial.** |
| 7 | **`@iconify/vue2`** (Vue-2-specific package) used in `common/IconifyIcon.vue` and `common/Iconify.vue`. | 2 files | Swap to `@iconify/vue` (v4+, Vue 3-compatible) - **this project already uses exactly that package** in `apps/whoobe-studio`/`apps/admin-dashboard` (added earlier this session for the ported `ColorPalette.vue`/icon work), so the target dependency is already proven working in this monorepo. Note: `blocks/helpers/IconFinder.vue` uses a *different*, version-agnostic mechanism (`@iconify/iconify`'s web-component-style `<i class="iconify" data-icon="...">`) that needs no change at all. | **Low** - small, well-understood, and the replacement is already in use elsewhere in this repo. |
| 8 | **`@tiptap/vue-2`** used only in `BlockTipTap.vue`. | 1 file | Swap to `@tiptap/vue-3` (official equivalent, same `Editor`/`EditorContent` API) - the extension packages (`@tiptap/starter-kit`, `@tiptap/extension-image`) are framework-agnostic core and need no change. | **Low**, one file. |

## 4. Data-model compatibility with this monorepo's existing schema

This matters regardless of which integration option gets picked tomorrow (§7), because migrated Pimcore documents already live in `cms_documents.root_block` as `WhoobeBlockNode` trees (`packages/core/src/cms/block-schema.ts`), and any editor we point at them needs a translation in both directions.

`WhoobeBlockNode` (existing): `{ id, type, name, tag?, style?, props?, content?, children?, dataBinding? }` - deliberately minimal, generic `props: Record<string, any>` bag.

`Element` (this repo): far more structured and *specific* - `css.{css,container}` (Tailwind strings, split into "self" vs "container" classes - a distinction `WhoobeBlockNode` doesn't have), `tailwind` (structured per-attribute customizer state), `alpine`, `events`, `gsap`, `data` (type-specific), `image`, `link`/`anchor`, `editable` (explicit flag, vs. our implicit type-based editability), `helper`/`dialog` (wizard metadata).

**Assessment: mapping is feasible in both directions but lossy without deliberate schema extension.** A round-trip `WhoobeBlockNode → Element → WhoobeBlockNode` would need to either (a) fold `Element`'s extra fields into `WhoobeBlockNode.props` (keeps our schema unchanged, but means our own preview renderers - `BlockNodePreview.vue`/`StudioBlockPreview.vue` - would need to grow support for `props.alpine`/`props.gsap`/etc. to actually render what was authored), or (b) extend `WhoobeBlockNode` itself with these as first-class optional fields (cleaner long-term, but touches `block-schema.ts`'s Zod schema and both existing preview renderers). This is exactly the kind of decision that belongs in tomorrow's integration conversation, not something to pre-decide here - flagging it now so it's not a surprise mid-port.

## 5. Phased porting plan

**Phase 0 - Spike: DONE, see `apps/whoobe-one-spike/`.** Stood up a bare Vue 3 + Vite shell (new app, not integrated anywhere else in this monorepo, own port 3006), ported `ElementsClass.js`/`BlocksClass.js`/`DatabaseClass.js` verbatim (confirmed: compiled completely unchanged, only needed a hand-written `.d.ts` shim alongside `ElementsClass.js` since strict-mode TS over-narrows the untyped class's dynamic fields - not a change to the source file itself), and rewrote `BlockElement.vue`/`BlockContainer.vue`/`BlockEditor.vue` fresh in `<script setup>` with buses swapped to `mitt` and `$attrs` converted to real declared props. Full rationale, every deliberate deviation from the source (z-index-ladder hit-testing replaced with `@click.self`, one shared `dragula` instance instead of one per container, two real source bugs fixed rather than reproduced, the dragula-vs-Vue-reactivity duplicate-node fix), and what's still unverified (no headless browser available in this environment to confirm actual click/edit/drag behavior interactively - typecheck, production build, and full module-graph transform all confirmed clean instead) are documented in `apps/whoobe-one-spike/README.md`. **Next action before Phase 1: open the dev server and manually confirm the interaction loop actually works** - that's the one thing this pass couldn't self-certify.

## 6. Open risk, not yet resolved: Tailwind version mismatch

This repo pins `tailwindcss: "npm:@tailwindcss/postcss7-compat@^2.2.16"` with PostCSS 7 - a Tailwind v2-era build, despite the README claiming "TailwindCSS 2.0 min." This monorepo's own Tailwind setup (built earlier this session for the header-brick Tailwind conversion work) is Tailwind **v4**. `tw.classes.js` (606 lines) is a hardcoded whitelist of utility class names driving every customizer control - some of Tailwind's utilities were renamed/restructured between v2 and v4 (e.g. gap utilities, aspect-ratio, arbitrary-value syntax maturity, container queries didn't exist in v2 at all). **This means the ported customizer UI may offer or produce classes that don't exist, or behave differently, under this monorepo's actual Tailwind v4 build - `tw.classes.js` needs an explicit audit against Tailwind v4's real utility set, not just a mechanical file copy.** This is independent of the Vue 2→3 port itself and should be scoped as its own verification pass once the port compiles, not assumed to be "free" alongside the JS-level porting work.

## 7. Integration options (for tomorrow's decision - not decided here)

Three genuinely different paths, each with real tradeoffs:

**A. Full replacement.** Retire the custom-built `apps/whoobe-studio` editor (tree + JSON-form-plus-brick-preview, built earlier this session) entirely; the ported `whoobe-one-studio` becomes the one editor. Requires a bidirectional `WhoobeBlockNode ↔ Element` adapter (§4) so migrated Pimcore documents can load into it and save back to `cms_documents`. Highest ceiling (genuinely best editing experience of anything evaluated this session), highest cost (full port + adapter both required before anything is usable), and the biggest open question is whether Pimcore-specific concepts this session already built real support for - Areablock/Areabrick field mapping, the per-document "Snippets in this Document" outline, DAM-backed image resolution - have an obvious place in `whoobe-one-studio`'s generic-element model or need to be bolted on.

**B. Side-by-side, different use cases.** Keep the current custom editor specifically for Pimcore-migrated-brick editing (it already understands Areablock/Areabrick fields, which is a genuinely different problem than freeform page-building); integrate the ported `whoobe-one-studio` as a separate tool for freeform/from-scratch page or snippet building, storing its own `Block`/`Element` JSON as-is (possibly literally in the new `cms_snippets` table added earlier this session, or a new one) rather than forcing a shared schema. Lowest integration risk, but means maintaining two editors long-term and users context-switching between them depending on content origin.

**C. Cherry-pick the editing mechanism only.** Take just the inline-`contenteditable` + `dragula` + recursive-container rendering approach (§1.2's `BlockElement.vue`/`BlockContainer.vue` core) and rebuild the *interaction model* inside the existing `apps/whoobe-studio` app, on top of the existing `WhoobeBlockNode` schema (extended per §4 as needed) - replacing the current split-pane tree+JSON-form editing UX with genuine inline editing, without adopting `whoobe-one-studio`'s Tailwind-customizer panels, GSAP/Alpine support, dialog-bus system, or Dexie-backed library/gallery features at all. Smallest scope, fastest to a visibly-better editing experience, but leaves the richest parts of `whoobe-one-studio` (the customizer, snippet library, GSAP/Alpine authoring) unused.

A fourth axis independent of A/B/C: **whether to keep Dexie/IndexedDB as this tool's storage at all.** `whoobe-one-studio`'s "no server, no database" design is a deliberate feature for its standalone use case, but this monorepo already has a real Postgres-backed `core-api` (`cms_documents`, the new `cms_snippets` table). If integrated (any of A/B/C), local-browser-only storage is very likely wrong for this project's actual needs - real persistence should go through `core-api`, with Dexie either dropped or repurposed as an offline-cache layer only. Worth deciding explicitly rather than porting the storage layer unexamined.

## 8. Effort summary

~11,675 lines of `src/` across ~150 files. Roughly:
- **~35% (scripts + data files + Vuex modules)**: mechanical, low-risk, much of it literally unchanged (`templates.js`, `tw.classes.js`, `animations.js`, `DatabaseClass.js`, `grid.js`).
- **~45% (the ~57 surveyed `.vue` files in common/dialog/media/gallery/helpers/preview/tailwind-controls + the ~25 block control panels)**: mechanical but high-volume - the `$attrs`→props conversion and bus-call renames dominate, embarrassingly parallel across files, no single file individually hard.
- **~20% (the core editing loop: `BlockEditor`/`BlockElement`/`BlockContainer`, the five event buses, the four global-method plugin files, TipTap, the preview/export path)**: genuine design attention needed, not just mechanical - this is where Phase 0's spike derisks the highest-uncertainty piece before the rest is attempted.

No single blocker found that would make the port infeasible. The real open decisions are integration-shaped (§7), not technical-feasibility-shaped.
