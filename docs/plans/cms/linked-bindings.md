# Linked bindings: a click in one list filters another (catalogue > categories > products)

Date: 2026-10-13. Status: in progress (first phase).

## The need

On one page or snippet, a first binding shows a list (categories) and a second binding, which may come from **another** source (another Data Class or another Integrations endpoint), shows the related records (products). When the visitor clicks a category, the products of that category are shown.

## Decision

A named **selection** that elements publish and lists listen to. Phase 1 filters **in the browser** the list the second binding already loaded; phase 2 (later) re-queries the source on each selection, for catalogues that do not fit in one list. The configuration is the same in both phases, so phase 2 changes nothing for authors.

Answers given by the author of the request:
- the two bindings can be of different kinds (Data Objects or Integrations) and different sources;
- the second list is limited to **100** records (the binding's `limit`) or uses its own pagination;
- **no initial choice**: with nothing selected the second list is empty (configurable: show all);
- the selection is in the URL (`?category=12`): shareable, and the back button works.

## Data model

New optional property `selection` on an element (`ElementSelection`, `@whoobe-cms/schema`):

```ts
selection?: {
  publish?: { name: string; field: string } | null          // the items of this repeater set the selection when clicked
  listen?:  { name: string; field: string; whenEmpty?: 'none' | 'all' } | null  // this repeater shows the items whose field equals it
}
```

- `name`: letters, digits, `-` and `_`, up to 32 characters (it is also the URL parameter).
- `field`: a Data Class attribute, or a dot path in the item of an Integrations list (as in `fieldPath`).
- The element is a **container with a binding** (a repeater). One container can publish and listen (categories > subcategories > products).
- A field that holds a list (tags) matches when any of its values equals the selection.

## How it renders

- The renderer (`walk.ts`) puts attributes on every repeated item: `data-whoobe-select` / `data-whoobe-value` (publisher), `data-whoobe-listen` / `data-whoobe-key` (listener). A listener without a selection is rendered hidden (`display:none`) so the server output has no flash.
- `mountSelection()` (`@whoobe-cms/renderer`, `selection.ts`) is the browser part: one click / keyboard handler for the document, state per name, URL (`pushState`, `popstate`), `aria-pressed` and `data-whoobe-selected="true"` on the chosen item (style it with `data-[whoobe-selected=true]:...`), and it shows or hides the listening items. A `whoobe-select` event is fired on every change. It reapplies itself when the framework re-renders the list.
- Clicking the selected item again clears the selection. Any element with `data-whoobe-select="name"` and `data-whoobe-value="x"` (Attributes panel) also sets it, and an empty value clears it: this is how a "All" button is made.
- React, Vue and Svelte `WhoobePage` call `mountSelection()` (so Next.js and Nuxt sites get it).
- The editor's Preview filters before its own pagination. The edit canvas shows every item and does not react to the click (a click there selects the element to edit).

## Limits of phase 1

- The mobile app generator has its own renderer: not included.
- A listening repeater is not paginated in the published output (the published repeaters are not paginated today); keep the binding's `limit` at 100 or less.
- Hidden items are in the page source: do not use it to keep data private.

## Dynamic bindings (added 2026-10-14)

A selection can also be a **route parameter**: `gatewayBinding.params = { id: '{selection.category}' }` on a route such as `catalogue/category/{id}`.

- The server cannot know the visitor's choice: the walker renders such a container empty, does not call the gateway for it, and marks the descriptor (`dynamicList: { selections, urlParams }`).
- In the browser the adapter (React `useDynamicChildren`, Vue `WhoobeNode`, Svelte `WhoobeContainer` + `dynamic.js`) calls `resolveDynamicChildren()` of the renderer at load (a choice kept in the address) and at every change of the selection. It substitutes `{selection.x}`, resolves the binding (`/api/v1/gateway/resolve`, which already accepts `params` for the names saved with the binding) and walks the container's children for each item with the same walker as the server (`walkGatewayValue`), so formatting, images and links match. An empty selection gives an empty list; a gateway error keeps what is shown; a stale answer is dropped.
- The browser never holds the site key: `ApiClient.gatewayResolveProxyPath` (`createWhoobeApi(..., submitPath, resolvePath)`) posts to the site's own route, generated by `packages/publish` (`app/api/whoobe-gateway-resolve/route.ts` for Next.js, `server/api/whoobe-gateway-resolve.post.ts` for Nuxt), which forwards only `bindingId` and `params` with the key.
- Editor: `resolveTree` does not fetch such a list, the Preview loads it when the selection is made (`BlockContainerPreview.vue`), the picker offers `{selection.name}` and says why it cannot preview; a binding with selection parameters is never turned into a relative one by the nested-bindings authoring.
- Verified in a real browser with the React, Vue and Svelte adapters (initial empty, click, other click, clear, `?category=` at load) and in the editor Preview.
- Not done: a Data Class query with a `{selection.x}` filter, the mobile app, a single bound text outside a container.
