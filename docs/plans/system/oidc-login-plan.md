# OIDC login for staff

Release 0.2, block A2. The plan row: *authorization-code with PKCE against any OIDC provider; roles mapped from a claim or assigned on first login. Local accounts stay (break-glass). SAML and LDAP are not built: a broker (Keycloak) covers them. Done when: login with Keycloak in the disposable stack; a deactivated user at the provider cannot start a new session; tests for the mapping and for a forged token.*

## What exists

Local accounts (e-mail, password, optional TOTP), sessions in the database (`wcms_session`, 7 days). The check of an identity provider's token (signature from the JWKS, `iss`, `aud`, `exp`, `nbf`, algorithm allow-list, key rotation) exists for the API clients of the gateway; it is moved to `packages/core/src/gateway/jwt-verify.ts` so core-api can use it for the ID token (step 1, done; the gateway re-exports it).

## Decisions

- **One provider per installation**, configured in the dashboard (Security > SSO), stored in a single-row table `oidc_settings` (migration 0062). Not environment variables: an administrator changes it, the audit log shows who. The client secret (optional: a public client with PKCE alone is accepted) is encrypted with `INTEGRATION_SECRETS_ENCRYPTION_KEY` and never returned, only "set".
- **Flow:** `GET /auth/oidc/login` creates `state`, `nonce` and a PKCE `code_verifier` (S256), keeps them in memory for 10 minutes (same single-process trade-off as the MFA challenges) and sets a short `wcms_oidc` cookie with a random binder whose hash is kept with them, so a callback that was not started by this browser is refused (login CSRF). Then it redirects to the provider's `authorization_endpoint` (from the discovery document, read through the outbound guard `safeFetch`). `GET /auth/oidc/callback` checks `state` and the binder, exchanges the code (client secret by HTTP Basic when there is one), verifies the **ID token** with the moved verifier (issuer, audience = client id, signature, expiry, `azp` when several audiences) and the `nonce`, then opens the ordinary session and redirects to the dashboard. Any failure redirects to `/?sso_error=<code>` with a short code, the cause goes to the log. The token response's access and refresh tokens are discarded: Whoobe keeps no token of the provider.
- **Who the person is:** the pair (`iss`, `sub`) in `user_identities`. First sign-in with an unknown pair: if a local user has the same e-mail **and the provider says `email_verified: true`**, the identity is linked to it (the setting `linkByEmail`, on by default; off = never link, always provision); else, with `autoProvision` on, a user is created (random unusable password hash, display name from `name`); else the sign-in is refused. An e-mail that is not verified never links or provisions.
- **Roles:** `roleClaim` (a claim name or dotted path, `roles`, `groups`, `realm_access.roles`) and a mapping *claim value → role*. At **every** sign-in the roles in the mapping are made to match the claim exactly (granted when the value is present, removed when not); roles outside the mapping (given by hand) are untouched. A new user whose claims match nothing gets `defaultRoleIds`; a person who would end up with no role at all is refused ("no access has been given to this account"). So removing someone from a group at the provider takes the role away at their next sign-in.
- **A deactivated user at the provider** cannot authenticate there, so cannot start a new session. A user deactivated in Whoobe (`is_active` false) is refused at the callback. Sessions already open run to their end (7 days) - the same limit as for local accounts; the audit log and the user list can end them (deactivating a user already ends theirs).
- **Second factor:** the local mandatory-2FA setting applies to the password login. A person who signs in through the provider uses the provider's factor; Whoobe does not ask a second time. Said on the settings screen and in the docs.
- **Local accounts stay.** `localLogin`: `all` (default) or `admins` (the password form works only for users who can manage users; everybody else must use the provider). Never "none": an installation must not be able to lock itself out when the provider is down; the break-glass is the administrator's local account, and the shell script.
- **Redirect URI:** `<redirectBaseUrl>/auth/oidc/callback`, `redirectBaseUrl` is a setting (the public address of the dashboard; behind nginx and in the Vite dev server `/auth` reaches core-api). The return address after login is always `redirectBaseUrl + '/'`, never a value from the request (no open redirect).
- **Provider addresses** (issuer, discovery) must be https, or http outside production; they go through the outbound guard. A provider on a private address needs `OUTBOUND_ALLOW_PRIVATE` (default true) - the same rule as every other outbound call.
- **Audit:** the settings change is audited (`setting.oidc_update`, secret "changed"); each SSO sign-in that creates a user, links an identity or changes roles is audited as an event (`user.sso_provision`, `user.sso_link`, `user.sso_roles`) with the actor "system:oidc".
- **Not built:** SAML, LDAP, several providers, single logout / back-channel logout, refresh of the provider session, SCIM provisioning, group-based deprovisioning without a sign-in. A broker (Keycloak) in front covers SAML and LDAP.

## Steps

All seven steps done 2026-10-19 (steps below). The redirect and the landing address became two settings (`dashboardUrl`, migration 0063), see CHANGES.

1. Move the token verifier to core. **Done.**
2. Migration 0062 (`oidc_settings`, `user_identities`), schema, records, secret encryption; pure helpers (claim path, role mapping, return URL, PKCE); unit and integration tests.
3. The protocol module (discovery, authorization URL, code exchange, ID token check) and the routes (`/auth/oidc/config`, `/login`, `/callback`; `GET`/`PUT /oidc-settings`, `POST /oidc-settings/test`); route contract, audit specs, nginx prefix; `localLogin` on `/auth/login`.
4. API tests against a mock provider written for the test (discovery, authorization, token, JWKS, keys it generates): good sign-in, forged signature, wrong audience / issuer / nonce / expired, replayed state, callback from another browser, unverified e-mail, link by e-mail, provisioning, role mapping both ways, deactivated user, `localLogin: admins`.
5. Dashboard: the "Sign in with ..." button and the error text on the login screen; the settings card.
6. A real Keycloak (the image is on the machine) in the disposable stack: realm, client, a user, a group mapper; sign in through a browser test; deactivate the user at Keycloak and show a new sign-in fails.
7. Docs (authentication page, a Keycloak / Entra / Okta how-to, configuration, API reference, threat model, status summary), CHANGES.
