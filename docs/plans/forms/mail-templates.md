# MAIL TEMPLATES

Mail Templates are a system to compose simple text/rich-text email templates used by the app, with dynamic data. Most mails are generated by the app - after form submissions, or after other website/backend events - so templates must be able to pull live data into the body.

Example (a contact-form notification, personalized after submission):

```
Hello {form.firstname} {form.lastname}, thank you for contacting us ...
```

## Context

### What exists today

- **Form notifications already work, but a "mail template" is a `whoobe_pages` row.** `formConfig.notify.templatePageId` points at a page whose Element tree is rendered to static HTML by `renderMailTemplate()` (`packages/core/src/mail/render-mail-template.ts`), then sent via `sendMail()` (`packages/core/src/mail/mailer.ts`). Bindings resolve **only** through the editor's `dataBinding` nodes (`applyTransform`/`escapeHtml`, ported in `field-transforms.ts`) - there is no `{placeholder}` syntax anywhere.
- **SMTP, sending, and auditing exist.** `mail_settings` (single global row), `mailer.ts`, and the `mail_log` table built for Settings → Mail → Log (bodies stored, preview modal, resend).
- **The editor already embeds.** `apps/admin-dashboard` opens whoobe-one-spike for a page via `WhoobeOneEmbed.vue` → `/editor?pageId=...&parentOrigin=...`; the editor loads/saves that page itself through `database-actions.ts` (`loadPage`/`savePage` → `pages-api.ts` → `whoobe_pages`).

### What this plan adds

A real **Mail Templates** entity - dedicated, reusable, not a page - with:

1. **Two kinds**: plain-text templates and rich HTML templates.
2. **Placeholder dynamic data**: `{namespace.field}` tokens that work in text templates, HTML templates, and subject lines.
3. **Management from Settings → Mail**: create as many templates as needed; HTML templates edited in the whoobe-one-spike editor, text templates via a textarea.
4. **Form notifications reference a Mail Template**, not a page - while legacy page-based notify configs keep working.

## Considerations (design decisions)

### C1. Storage: a new `mail_templates` table, not `whoobe_pages`

A mail template is not a routable page. `whoobe_pages` carries page-only concerns (unique slug, translation groups, locale, publish gate, SEO/sitemap/search metadata) that a mail template neither needs nor wants. A dedicated table carries exactly the mail-relevant fields, including a `kind` discriminant (`html` | `text`) and a default `subject`.

**Transition**: existing saved Forms reference `notify.templatePageId` (a `whoobe_pages` id). The new `mailTemplateId` is the primary field; the submit route falls back to resolving `templatePageId` as a page and rendering it with the existing renderer, so nothing already saved breaks. Admins migrate a page-based template to a real one by re-selecting it from the Templates list.

### C2. Two rendering mechanisms, one token engine

- **HTML templates**: the Element tree rendered by `renderMailTemplate()` as today (dataBinding nodes, `applyTransform`, escaping), **plus** `{namespace.field}` token substitution in leaf text content as a post-pass. The two mechanisms coexist: dataBinding stays available for richer output (links, transforms, images); tokens are the universal personalization syntax.
- **Text templates**: plain text with `{namespace.field}` tokens, substituted by the same engine.
- **Subject lines**: token substitution for both kinds.
- One shared token engine (`substituteTokens(text, context)`) keeps behavior identical across all three call sites.

### C3. Data context and namespaces

Every render receives a `context` object, not a bare submission:

```ts
{ form: {...submission}, site?: {...}, user?: {...}, object?: {...} }
```

- Tokens resolve by dot-path against the context: `{form.firstname}` → `context.form.firstname`.
- HTML `dataBinding.field` (e.g. `firstname`) continues to resolve against `context.form`, so existing page-based templates render identically. A namespaced field (`form.firstname`) is stripped to the same lookup.
- Today the only populated namespace is `form` (the submission). Future triggers (workflow transitions, user invitations, AI generation) build their own context - `site.*`, `user.*`, `object.*` - without renderer changes.

### C4. Editor integration

HTML templates are edited in the embedded whoobe-one-spike editor, mirroring the page flow:

- New query param `/editor?mailTemplateId=...` (+ `parentOrigin`), handled in `Editor.vue` like `pageId`.
- New `loadMailTemplate(editor, id)` / `saveMailTemplate(editor)` in `database-actions.ts` (plus a `mail-templates-api.ts` client in whoobe-one-spike), and a flag on the editor store so the editor's Save writes to `mail_templates` instead of `whoobe_pages`.
- Text templates need no editor - a textarea + subject form in the admin dashboard.

### C5. Security

- Every token substitution **HTML-escapes** the resolved value (a mail template's bound field is typically public, visitor-submitted input - same reasoning the existing `escapeHtml` in `render-mail-template.ts` already applies to dataBinding values). No double-encoding: each mechanism handles its own content.
- Subject-line substitution strips CR/LF and control characters (header-injection guard) - a form's subject field can contain `{form...}` values.
- Templates themselves are admin-authored content stored as jsonb/text and rendered as-is (trusted), consistent with pages.

### C6. Form notify config

`formConfig.notify` gains `mailTemplateId` (a `mail_templates` row). The existing `recipientEmail` and `subject` override fields stay; a blank `subject` falls back to the template's default. The server loads the template by id, renders by kind with `context = { form: parsed }`, and sends.

### C7. Reuse beyond forms

`sendMailFromTemplate(template, context, { to, cc?, subject? })` in `packages/core` becomes the single path for any app email - form notifications today, workflow/user/AI emails later. It renders (by kind), sends via `sendMail()`, and the existing `mail_log` records every attempt (body stored, preview/resend available) automatically.

### C8. Permissions

Template CRUD is gated on `PERMISSIONS.SETTINGS_MANAGE`, matching `mail_settings`/`mail_log`.

## Plan

### 1. Schema

New `packages/core/src/db/mail-templates-schema.ts`:

```ts
export const mailTemplates = pgTable('mail_templates', {
  id: uuid('id').primaryKey().defaultRandom(),
  name: text('name').notNull(),
  kind: text('kind').notNull(),          // 'html' | 'text'
  description: text('description'),
  subject: text('subject'),              // optional default subject, tokens allowed
  content: jsonb('content'),             // html kind: Element tree
  body: text('body'),                    // text kind: plain text
  createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
  updatedAt: timestamp('updated_at', { withTimezone: true }).notNull().defaultNow(),
});
```

`kind` is plain text, not an enum - new kinds (e.g. markdown) can be added without a migration. Exactly one of `content`/`body` is populated, depending on `kind`.

Added to `packages/core/drizzle.config.ts` schema list; a new drizzle migration (`mail_templates` table) generated and applied.

### 2. Records

New `packages/core/src/db/mail-templates-records.ts`: `listMailTemplates()` (newest first, metadata + kind only), `getMailTemplate(id)` (full row), `createMailTemplate`, `updateMailTemplate`, `deleteMailTemplate`. Standard pattern identical to `whoobe-one-template-records.ts`.

### 3. Renderer

`packages/core/src/mail/render-mail-template.ts`:

- Generalize to a context-aware entry point. Keep the existing `renderMailTemplate(pageContent, submission)` signature working (it maps to `context = { form: submission }`), and add `renderMailTemplateFromRecord(template, context)` that dispatches on `kind`:
  - `html`: Element-tree render as today, then `substituteTokens` over every resolved text node's output, then return the full HTML.
  - `text`: `substituteTokens(template.body, context)`.
- New `packages/core/src/mail/token-substitution.ts`: `substituteTokens(text, context): string` - matches `{([a-zA-Z0-9_.]+)}`, resolves the dot-path against `context` (missing/undefined → empty string), HTML-escapes the value. `substituteTokensPlain(text, context)` for subject lines (no HTML escaping, but strips `\r`/`\n`/control chars).
- HTML `dataBinding.field`: resolve against `context.form` when unnamespaced; accept a `form.` prefix.

### 4. Mailer helper

`packages/core/src/mail/mailer.ts`:

```ts
export async function sendMailFromTemplate(input: {
  template: MailTemplateRecord;
  context: Record<string, unknown>;
  to: string;
  cc?: string;
  subject?: string;   // overrides the template's default
}): Promise<void>
```

Renders subject + body by kind, then calls the existing `sendMail()` (which already logs to `mail_log`). Throws if mail settings aren't configured - callers decide whether that's fatal.

### 5. Backend API

`apps/core-api/src/server.ts`, all `requirePermission(PERMISSIONS.SETTINGS_MANAGE)`:

- `GET /mail-templates` → `{ templates: [...] }` (metadata only: id, name, kind, description, subject, updatedAt).
- `POST /mail-templates` → create (`name`, `kind`, `description?`, `subject?`, `content?`, `body?`; validate `kind` is `html`|`text`).
- `GET /mail-templates/:id` → full row (includes `content`/`body`).
- `PATCH /mail-templates/:id` → update; 404 if missing.
- `DELETE /mail-templates/:id` → delete.

### 6. Form notify wiring

In `POST /public/forms/:classId/submit`, replace the notify resolution:

1. `notify.mailTemplateId` set → `getMailTemplate(id)` → `renderMailTemplateFromRecord(template, { form: parsed })` → `sendMailFromTemplate({ template, context: { form: parsed }, to: notify.recipientEmail, subject: notify.subject || template.subject || undefined })`.
2. else `notify.templatePageId` set (legacy) → `getWhoobePage(id)` → `renderMailTemplate(page.content, parsed)` → `sendMail` as today.

Still wrapped in its own try/catch - a failing mailer must never turn a successful Data Object write into a `500`.

### 7. Editor integration (whoobe-one-spike)

- New `apps/whoobe-one-spike/src/mail-templates-api.ts`: `listMailTemplates()`/`getMailTemplate(id)`/`createMailTemplate`/`updateMailTemplate` (same shape as `pages-api.ts`).
- `database-actions.ts`: `loadMailTemplate(editor, id)` (mirror `loadPage`) and `saveMailTemplate(editor)` (create-or-update `mail_templates`, mirror `savePage`).
- Editor store: a `mailTemplateId` field + `isMailTemplateMode` flag (or reuse the single flag) so `BlockEditor.vue`'s save handler calls `saveMailTemplate` instead of `savePage`.
- `views/Editor.vue`: read `mailTemplateId` query param → `loadMailTemplate`; otherwise fall back to `pageId`/demo seed.

### 8. Admin dashboard UI

- New `apps/admin-dashboard/src/utils/mail-templates-api.ts` client (list/get/create/update/delete).
- `MailSettingsCard.vue` gains a fourth tab **Templates** (alongside Settings / Email Test / Mail Log):
  - List table: name, kind badge, subject, updated, actions (Open / Delete).
  - "New template" + edit form: name, kind select, description, subject; for `text` kind an inline textarea for `body`; for `html` kind an embedded editor.
  - HTML-template editor: new `MailTemplateEditorEmbed.vue` mirroring `WhoobeOneEmbed.vue` (`/editor?mailTemplateId=...&parentOrigin=...`), shown full-width in the card when a template is open. The editor's own Save persists to `mail_templates` (per §7).
- Card header: rename from "Outgoing Mail" to "Mail" (the doc's "remove Outgoing") now that it hosts settings, test, log, and templates.

### 9. Migration / backfill

- Drizzle migration for `mail_templates` (no backfill of `whoobe_pages` templates into it - they stay reachable via the legacy fallback; admins convert on demand by selecting the template in Form config).

## Resolved (2026-08-15)

Implemented per the plan above:

- **Storage**: new `mail_templates` table (schema/records/migration 0025) - `name`, `kind` (html|text), `description`, `subject`, `content` (Element tree jsonb), `body` (plain text).
- **Renderer**: `render-mail-template.ts` is now context-aware (`renderTemplateContent(content, context)`; the legacy `renderMailTemplate(pageContent, submission)` maps to `context = { form: submission }`). `dataBinding` fields resolve against `context.form` (unnamespaced, keeping page-based templates identical) or via a `form.`-prefixed dot-path, and a final `{namespace.field}` token-substitution pass runs over the whole HTML. New `token-substitution.ts` (`substituteTokens`, HTML-escaping values; `substituteTokensPlain`, CR/LF-stripping for headers; shared `resolveContextPath`).
- **Mailer**: new `sendMailFromTemplate({ template, context, to, cc?, subject? })` renders by kind and sends through `sendMail()`, so every template-driven email lands in `mail_log` with its stored body.
- **API**: `GET/POST /mail-templates`, `GET/PATCH/DELETE /mail-templates/:id` (all SETTINGS_MANAGE); the list returns metadata only. Form notify wiring in `POST /public/forms/:classId/submit` now prefers `notify.mailTemplateId` and falls back to the legacy `notify.templatePageId` (whoobe_pages) so already-saved Forms keep working.
- **Editor**: `ElementsClass`'s `formConfig.notify` gains `mailTemplateId`; `FormConfigControl.vue` offers a mail-template select (with the legacy page select still present); whoobe-one-spike has a `mail-templates-api.ts` client, `loadMailTemplate`/`saveMailTemplate` in `database-actions.ts`, a `mailTemplateId` flag on the editor store, `/editor?mailTemplateId=` support in `Editor.vue`, and `BlockEditor.vue`'s Save branches to `saveMailTemplate` (no path prompt, no Save-As/slug chrome in mail mode).
- **Admin UI**: `utils/mail-templates-api.ts` + a **Templates** tab in `MailSettingsCard.vue` (list with kind badges, inline text-template editor, `MailTemplateEditorEmbed.vue` iframe for HTML templates; new HTML templates are created first, then opened in the editor).

Verified: typecheck clean across `packages/core`, `core-api`, `whoobe-one-spike`, `admin-dashboard`; all 59 core tests pass. Smoke-tested against the live DB/API: token escaping (`{form.message}` → `&lt;script&gt;...`), header-injection guard (CRLF in a substituted subject value → spaces), text-template rendering, HTML-template rendering mixing dataBinding + tokens, legacy page-path render, template CRUD (create/update/list/get/delete), and a full `sendMailFromTemplate` send that arrived in mailhog and was logged with its rendered body. Not exercised in a browser this pass - building a mail template in the embedded editor UI and submitting a real form with `mailTemplateId` set hasn't been tested interactively.

Follow-up fixes (same day): the HTML-template editor no longer comes up as a dead/empty canvas for a brand-new template (`loadMailTemplate` seeds an empty document root when content is null, `saveMailTemplate` seeds defensively too, and a failed template fetch in `Editor.vue` seeds an empty mail-template document with `mailTemplateId` still set so Save creates a fresh template rather than silently becoming a whoobe_pages save); the editor is presented full-page-width in the dashboard via a full-screen overlay opened from the Templates edit panel.

Email-correctness pass (same day): mail bodies now render correctly in email clients. (1) **Inline styles from Tailwind classes** - the renderer compiles every element's utility classes to a `style` attribute via `tailwind-inline.ts` (`tw-to-css`, cached per class string, interaction variants dropped), since clients don't load the editor's stylesheet and bare `class="p-8 flex flex-col..."` rendered as unstyled text. (2) **Static content is sanitized HTML, not escaped text** - the editor stores contenteditable innerHTML (real `<b>`/`<a>` markup) into `content`, so `escapeHtml` was destroying formatting; `sanitizeInlineHtml()` whitelists safe tags, drops attributes except safe link `href`s, and still escapes anything dangerous; bound (public) values stay fully escaped. (3) **Text-kind bodies substitute without HTML-escaping** (`substituteTokensPlain`, control chars stripped) so text/plain output doesn't show literal `&amp;`/`&lt;`.

Dynamic recipient (same day): `mail_templates` gains a `to` column (migration 0026) supporting `{namespace.field}` tokens, so a template can be addressed dynamically (`{form.email}`). `sendMailFromTemplate()` resolves the recipient - an explicit `to` (Form's `notify.recipientEmail`) wins, otherwise the template's `to` is token-substituted, throwing if nothing non-empty resolves; the form-submit notify path no longer requires a fixed `recipientEmail` when the template supplies a dynamic one. Admin Templates tab exposes a "To" field (form + list column).

Font family handling (same day): the editor's `font` field (Google Font family names) renders in emails via `mail-document.ts` - `fontFamilyStack()` gives every face a web-safe fallback (`"Open Sans", 'Segoe UI', Helvetica, Arial, sans-serif`, serif faces → Georgia), and `buildMailDocument()` wraps the body in a full HTML document whose `<head>` links the Google Fonts CSS for the families the template uses (`collectMailFonts()` walks the Element tree). Apple Mail/iOS Mail load the exact webfont; Gmail/Outlook strip it and use the fallback. Applied in `sendMailFromTemplate()` and the legacy `templatePageId` path; the mail log stores the full document so the preview modal renders identically.

BCC/CCN (same day): `mail_templates` gains a `bcc` column (migration 0027) supporting `{namespace.field}` tokens like `to`; `sendMailFromTemplate()` resolves it (explicit bcc wins, CR/LF-stripped) and the admin Templates tab exposes a "BCC / CCN" field. `mail_settings` gains a `bcc_from_address` flag (same migration): when on, every outgoing email is BCC'd to the configured from address ("keep a copy of everything we send"), merged with any explicit bcc in `sendMail()`. Exposed via `GET`/`PUT /mail-settings` and a Settings → Mail checkbox.

DAM images (same day): mail templates silently dropped images picked from the DAM because the editor stores a stable reference (Pimcore path / asset UUID), never a URL, and the renderer only emitted `<img>` for http(s) URLs. New `mail-image-urls.ts` (`resolveMailImageUrls()`/`looksLikeDamReference()`) walks the tree and resolves each reference to a stable public URL via the asset-processor's `/dam-asset/*` proxy (`S3_PUBLIC_BASE_URL` + object key) - serves objects regardless of visibility, never expires (unlike presigned URLs). `renderTemplateContent()`/`renderMailTemplate()` take an optional `imageUrls` map, resolved before rendering in `sendMailFromTemplate()` and the legacy `templatePageId` path; unresolvable references omit the `<img>`. `{form.field}` tokens in static content are verified working end to end.

Notify context fix (same day): form-notification emails render against the **raw submitted attributes** (honeypot-stripped), not the class-validated subset - `compileDynamicSchema().parse()` strips unknown fields (Zod `z.object()` default), so a form input like `message` that isn't a declared class field was dropped before the email rendered and `{form.message}` came out empty. The renderer escapes all values, so raw attributes are safe; the Data Object write still uses the validated `parsed`. (Note: non-class fields are therefore available in the email but not stored on the object - add the field to the Data Class if it should persist too.)
