# Native Class Authoring, Relations & Custom CRUD Views

Plan for making Whoobe CMS's Data Object system usable by a customer who has **no Pimcore install at all** - the founding principle this codebase has stated before (`whoobe-one-editor-integration-plan.md` §1, quoted again in `advanced-data-modeling-plan.md` §6 point 4) but never actually built for Data Objects. Sibling to, and building directly on top of, `docs/plans/datamodel/advanced-data-modeling-plan.md` (the real `data_classes`/`data_objects` schema, the dynamic form renderer, the migration pipeline) - this plan does not redesign anything that plan's Phases 0-7 already shipped, it fills the one gap that plan explicitly named and deferred.

---

## 0. Framing: migration is a data source, not the bootstrap mechanism

`advanced-data-modeling-plan.md` was written and executed entirely against one real goal: getting one real Pimcore install's classes and objects into Whoobe correctly. That work is real and done (Phases 0-7, 10 classes, 202 objects, full locale/relation/field-collection fidelity). But it means **every class in this system today exists because `migrate-classes` put it there** - there has never been another way for a `data_classes` row to come into existence, and the admin UI has no "Classes" page at all (confirmed: `SettingsView.vue` has `MfaSettingsCard`/`WorkflowSettingsCard`/DAM config only; `POST /data-classes` and `PATCH /data-classes/:id` and `DELETE /data-classes/:id` are real, working routes in `apps/core-api/src/server.ts:882-955` that nothing in `admin-dashboard` has ever called).

This plan's framing, stated explicitly because it changes what "done" means for the system as a whole: **`migrate-classes`/`migrate-objects` must stay an optional, explicitly-triggered import path, never a prerequisite.** A customer with no Pimcore history must be able to open the admin UI, define a class, add fields, relate it to another class, and start creating records - without the migration-tool package ever running. Nothing here is currently "automatic" in the sense of a cron job or startup hook (checked - no scheduler/cron code exists anywhere in `packages/migration-tool` or `apps/core-api`), so there is no automatic trigger to remove. The real gap is narrower and more specific than "make it on-demand": migration is already only runnable on-demand *by someone with shell and direct database access* (`migrate-classes`/`migrate-objects` are CLI commands, `packages/migration-tool/src/cli.ts`), which today is the *only* on-demand path to a class - because it's the only path, period. §4 makes it one option among several, and §4.4 optionally lifts it into the admin UI itself so "on demand" also means "by an admin, not a developer."

---

## 1. Scope & goals

Three deliverables:

1. **Class Builder** - a real admin UI to create, edit, and delete `data_classes` rows and their field lists from scratch, wired to the already-real `POST`/`PATCH`/`DELETE /data-classes` routes that exist today but have no caller.
2. **Relations, made reachable from the Class Builder** - the relation *engine* is already fully real (`compileFieldSchema()` in `packages/core/src/schema/dynamic.ts`, `useRelationOptions.ts`, and real single/multi relation pickers in `DataObjectFieldControl.vue:74-103`) and works for *any* class by name, migrated or not. The only missing piece is a way to set `relationTarget` (and pick a relation shape) without hand-editing a `fields` JSONB blob - this plan adds that picker to the Class Builder, not a new relation mechanism.
3. **Custom CRUD views** - today's object detail form (`DataObjectForm.vue`) renders every field as one flat vertical list in field-definition order, and the object list (`ObjectsView.vue:87-92`) has one fixed set of table columns (Key/Locales/Class/Status/Modification Date) for every class. Neither is configurable. This plan adds an optional, per-class view layout (grouping fields into sections for the detail form; choosing which fields appear as list columns) authored from the same Class Builder, with today's flat/fixed rendering staying the fallback when no layout is configured - so every existing migrated class keeps working unchanged.

**Explicitly not this plan's job**: redesigning `data_classes`/`data_objects` (`advanced-data-modeling-plan.md` §4 stands as-is - this plan only adds an optional `viewConfig`-shaped column, see §3.3), redesigning the publish/workflow gate (`object-publish-workflow-plan.md`, already integrated), or building a `fieldcollections` *authoring* UI (collection types remain something only `migrate-classes` can populate today via `collectionTypes` - see §5's open question on whether native classes need them at all in v1).

## 2. Where this stands today (verified against real code, not assumed)

- **Backend is already ahead of the frontend.** `data-classes` CRUD is fully real server-side: `GET /data-classes`, `GET /data-classes/:id`, `POST /data-classes`, `PATCH /data-classes/:id`, `DELETE /data-classes/:id` (`apps/core-api/src/server.ts:858-955`), all gated on the existing `PERMISSIONS.OBJECTS_READ`/`OBJECTS_WRITE` constants (`packages/core/src/auth/permissions.ts:7-8`) - the same permissions object create/edit already uses, so no new permission strings are needed. `apps/admin-dashboard/src/utils/data-classes-api.ts` and `stores/dataClassesStore.ts` exist but are **read-only callers** (list classes for the class-filter dropdown) - `createDataClass`/`updateDataClass`/`deleteDataClass` client functions don't exist yet.
- **The dynamic form and relation engine are already class-agnostic.** `compileDynamicSchema()`/`compileFieldSchema()` (`packages/core/src/schema/dynamic.ts`) and `DataObjectForm.vue`/`DataObjectFieldControl.vue` render and validate purely off a class's `fields: ClassFieldDefinition[]` array - nothing in that path checks whether the class came from `migrate-classes` or anywhere else. `useRelationOptions(className)` (`apps/admin-dashboard/src/composables/useRelationOptions.ts`) resolves a relation target purely by looking up `dataClassesStore.classes.find(c => c.name === className)` - a hand-authored class is exactly as valid a relation target as a migrated one, today, with zero changes needed. This is the plan's biggest piece of good news: **§1's "Relations" goal is almost entirely already built**, it just has no field-authoring UI in front of it.
- **`ClassFieldDefinition` already supports every field type the Class Builder needs for v1** (`packages/core/src/schema/dynamic.ts:20-30`): `name`, `title`, `fieldType`, `mandatory`, `localized`, `relationTarget`, `options`, `blockFields`. `collectionFields`/`collectionTypes` (Field Collections) also exist on the type but are deliberately out of scope for v1 authoring (§5).
- **No class management UI exists at all.** `SettingsView.vue` renders `DamConfigManager`, `MfaSettingsCard`, and `WorkflowSettingsCard` (`apps/admin-dashboard/src/views/SettingsView.vue`) - no `ClassSettingsCard` or equivalent. `ObjectsView.vue`'s class `<select>` (line 27-32) is populated from `dataClassesStore.classes` for *filtering/selecting*, never for *authoring*.
- **The object list has one fixed column set for every class.** `ObjectsView.vue:87-92`: Key/Path, Locales, Class, Status, Modification Date, Actions - identical regardless of which class's rows are shown. There is no per-class notion of "what should this list show."
- **The object detail form has one fixed layout for every class.** `DataObjectForm.vue` (`apps/admin-dashboard/src/components/objects/DataObjectForm.vue:1-9`) is a single `v-for` over `fields`, rendering one `DataObjectFieldControl` per field top to bottom - no grouping, sectioning, or tabbing beyond the locale sub-tabs `MasterObjectTab.vue` already provides (per-locale, not per-field-group).
- **Migration stays CLI-only.** `packages/migration-tool/src/cli.ts`'s `migrate-classes`/`migrate-objects` commands require shell access to a machine with DB/filesystem access to the source Pimcore install - there is no `core-api` route or admin-UI action that triggers either one. Confirmed no cron/scheduler anywhere in this codebase that could be running migration automatically - it was already "on demand" in that narrow sense, just not admin-reachable (§0, §4.4).

## 3. Design

### 3.1 Class Builder

New admin sub-page, same placement pattern `WorkflowSettingsCard.vue` already established under Settings (`SettingsView.vue`): a `ClassSettingsCard.vue` (or a dedicated `ClassesView.vue` if the list of classes + their field editors gets too large for a Settings card - a real call to make once the field editor's actual size is known, not decided here).

- **Class list**: name, label, field count, object count (reusing `dataClassesStore.classes` plus a count query), New/Edit/Delete actions.
- **Class editor**: `label` and `name` (name immutable after creation, matching how `whoobe_pages`' own slug-like identifiers are treated elsewhere - a real decision to confirm, since `data_objects` uniqueness keys off `classId` not `name`, so a rename is technically safe at the DB layer; still worth a deliberate choice rather than an accident).
- **Field list editor**: add/remove/reorder (drag or up/down, matching the Field-Collection editor's own "no drag-and-drop, ↑↓ buttons" precedent from `advanced-data-modeling-plan.md` Phase 6 - consistent with this codebase's stated "not required for v1" scoping elsewhere). Per field: `name` (identifier, immutable once objects exist against it - see guardrail below), `title` (display label, freely editable), `fieldType` (dropdown, scoped to the v1-supported subset - see below), `mandatory`, `localized`, and type-conditional extra inputs: `options` (comma-separated, for `select`/`multiselect`) and `relationTarget` (§3.2).
- **v1 supported field types**: `input`, `textarea`, `wysiwyg`, `numeric`, `checkbox`, `date`, `email`, `country`, `select`, `multiselect`, `manyToOneRelation`, `manyToManyRelation`, `link`. Deliberately excluding `block` (needs a recursive sub-field editor - real, buildable, but a genuine v2 addition once the flat case is solid) and `fieldcollections`/Field-Collection-specific types (§5) from the *authoring* UI - both remain renderable/valid (`compileFieldSchema()` already handles them) for classes that already have them from migration, just not something the Class Builder can create fresh in v1.
- **Guardrail: editing a field that already has data.** Renaming a field's `name` (not `title`) or narrowing its `fieldType` on a class with existing `data_objects` rows would silently orphan or invalidate stored `attributes` values (no migration-on-save exists, and shouldn't be invented here without a real reason to). v1 policy: the editor warns ("N existing objects have data in this field") and blocks a `name`/`fieldType` change outright rather than allowing a silent break - matching this codebase's repeated preference for an honest, stated limitation over a half-built auto-fix (`advanced-data-modeling-plan.md`'s own recurring pattern for exactly this kind of gap). Adding a new field or changing `title`/`mandatory`/`localized`/`options` on an existing field is unrestricted - none of those invalidate stored data.
- **Delete class**: only allowed with zero existing objects (mirrors why `DELETE /data-classes/:id` presumably has no cascade today - to confirm against the real route body, not assumed) - otherwise the UI must say why, not let the request 500/silently orphan objects.

### 3.2 Relations

No new data-layer or rendering engine work - `compileFieldSchema()`, `useRelationOptions()`, and the real pickers in `DataObjectFieldControl.vue:74-103` already handle every relation shape generically by class name. This section is entirely about exposing what already works:

- The Class Builder's field editor, when `fieldType` is `manyToOneRelation`/`manyToManyRelation`, shows a **relation target dropdown** populated from `dataClassesStore.classes` (any class, including the one being edited - self-relations, e.g. a `Category` with a `parentCategory` field, are not a special case anywhere in the existing engine and should not become one here).
- `manyToManyObjectRelation`/`advancedManyToManyRelation` (the two extra multi-relation fieldtypes Pimcore distinguishes, §4.3 of the sibling plan) stay migration-only distinctions - v1's Class Builder only offers plain `manyToManyRelation`, since nothing in this codebase's own storage (`data_objects.attributes` is one JSONB blob per row, not Pimcore's edge-table split, per the sibling plan §4.2's own explicit design choice) actually behaves differently across those three at the Whoobe layer - they compile to the identical `z.array(z.object({ id }))` shape today (`dynamic.ts`). Not a new distinction to invent for hand-authored classes.
- No object-relations edge table is needed for natively-created relations, confirming §4.2 of the sibling plan's "everything in one JSONB blob" decision already covers this case with zero extra schema work.

### 3.3 Custom CRUD views

Add one new, optional column to `data_classes`: `viewConfig: jsonb('view_config').$type<ClassViewConfig | null>()`, nullable, defaulting to `null` - every existing migrated class keeps rendering exactly as it does today (§2's fixed list columns / flat form) until an admin explicitly configures a layout, matching this plan's own additive, non-breaking posture everywhere else.

```ts
export interface ClassViewConfig {
  listColumns?: string[];          // field `name`s to show as extra table columns in ObjectsView.vue, in order; Key/Locales/Class/Status/Modification Date stay fixed regardless
  detailSections?: {
    title: string;
    fields: string[];              // field `name`s belonging to this section, in order
  }[];                              // any field not listed in any section falls through to a trailing "Other fields" section - never silently hidden
}
```

- **List view**: `ObjectsView.vue`'s table gains up to N extra columns (a reasonable cap, e.g. 5, to keep the table usable - exact number a real UI-review call, not fixed here) sourced from `viewConfig.listColumns`, rendering each row's `attributes[fieldName]` with the same lightweight per-type formatting the export logic (`data-export.ts`) already has to do (a real, small piece of shared logic worth factoring out rather than duplicating - concretely, stringifying a relation `{id}` vs. a plain string vs. an array).
- **Detail view**: `DataObjectForm.vue` renders `viewConfig.detailSections` as visually grouped blocks (headed subsections within the same tab, not new tabs - locale sub-tabs are already `MasterObjectTab.vue`'s job and shouldn't be doubled up with a second, competing tab concept) when present, falling back to today's single flat list when `viewConfig` (or `detailSections`) is absent.
- **Authoring**: the Class Builder (§3.1) gains a "View Layout" section - for list columns, an ordered multi-select over the class's own fields; for detail sections, a simple named-group editor (create a section, assign fields to it by checkbox, reorder sections) - explicitly not a drag-and-drop page-builder, consistent with every other "not required for v1" editor this codebase has already shipped (Workflow places/transitions, Field Collection type picker).

### 3.4 On-demand, admin-triggered Pimcore import (optional, lower priority) - DONE

Per §0's framing, this is explicitly an *addition*, not a prerequisite for §3.1-§3.3 - a customer with no Pimcore install gets full value from the Class Builder alone. Where this still adds real value: `migrate-classes`/`migrate-objects` used to require shell + direct DB/filesystem access to the source install, so "on demand" used to mean "on demand for a developer," not "on demand for an admin."

**Credential-storage question, resolved**: presented as a real choice (env-var-only, matching this codebase's own existing precedent for external-service credentials - `apps/asset-processor`'s S3/MinIO config, `DamConfigManager.vue`'s own "credentials are managed server-side only" - vs. admin-entered settings stored in Postgres). Admin-entered, stored settings was chosen for the flexibility (no redeploy needed to add/change a source, multiple sources supported) - a genuinely new pattern for this codebase, not a precedent it already had, so it gets real encryption at rest rather than following the weaker precedent already sitting in `users.totpSecret` (plain `text`, `auth-schema.ts`): a leaked Pimcore DB password is a materially bigger blast radius (read access to an entire external database) than one user's TOTP secret.

- **`migration_sources` table** (new, `packages/core/src/db/migration-sources-schema.ts`; migration `drizzle/0013_stormy_omega_red.sql`): `label`, `dbHost`, `dbPort`, `dbUser`, `dbPasswordEncrypted`, `dbName`, `classesPath`. `dbPasswordEncrypted` is AES-256-GCM ciphertext (`migration-sources-crypto.ts`, Node's built-in `crypto`, no new dependency - random IV per encryption, authenticated so a tampered/corrupted value fails to decrypt rather than silently yielding garbage credentials), keyed by a new `MIGRATION_SOURCE_ENCRYPTION_KEY` env var (scrypt-derived, so any-length operator-chosen secret works, not just a hand-generated 32-byte key). 4 new Vitest tests (`migration-sources-crypto.test.ts`) cover round-trip, non-determinism (random IV), tamper rejection, and the missing-key error path. The records layer (`migration-sources-records.ts`) strips `dbPasswordEncrypted` from every shape returned outside the file itself (`toRecord`) - only `getMigrationSourceConnectionConfig` (internal, used solely by the import routes to build a real DB connection) ever decrypts it; no route ever returns a password, encrypted or not, over HTTP.
- **`packages/migration-tool/src/cli.ts` refactored, not reimplemented**, per this section's own original intent: `migrateClasses(flags)`/`migrateObjects(flags)`'s real logic was extracted into exported `runClassMigration(options)`/`runObjectMigration(options)`, parameterized (`classesDir`/`sourceConfig` passed in, not read from `process.env`) and returning a structured `{ succeeded, failed, errors: {item, message}[] }` instead of only `console.log`-ing. The CLI's own `migrateClasses`/`migrateObjects` became thin wrappers that build the same options from env vars as before and call the shared functions - CLI behavior/output is unchanged (44/44 existing migration-tool tests still pass, confirming this). Both are now exported from the package's own `index.ts` for `core-api` to import directly.
- **`core-api` routes** (`apps/core-api/src/server.ts`, all gated on `PERMISSIONS.OBJECTS_WRITE` - the existing constant, not a new `objects:migrate` string, matching this plan's own §4/Phase-1 precedent of reusing existing permissions): `GET`/`POST`/`PATCH`/`DELETE /migration-sources` (CRUD for stored sources) plus `POST /migration-sources/:id/import-classes` (body: `dryRun`, `className`) and `POST /migration-sources/:id/import-objects` (body: `className` required, `dryRun`, `limit`) - both call `runClassMigration`/`runObjectMigration` directly with the resolved source's config, mirroring the CLI's own flag shape.
- **Admin UI**: a new `MigrationSourcesCard.vue` under Settings - **a separate card, not an action folded into `ClassSettingsCard.vue`** as this section originally sketched, a deliberate deviation once actually built: "import classes" has no single class to attach the action to (it's how new classes *arrive*), and `WorkflowSettingsCard.vue` already established this codebase's own precedent of "per-class admin actions get their own settings card, cross-referencing `dataClassesStore` for the picker" rather than living inside the class editor itself - consistent with that, not a departure from it. Each configured source shows inline "Import Classes" (optional class-name filter, dry-run) and "Import Objects" (a class picker - filtered to classes that already have a `pimcoreId`, since `runObjectMigration` requires one, real UX rather than surfacing a 500 the admin can't interpret - limit, dry-run) controls, with the last run's succeeded/failed counts and per-item error list shown inline.
- Verified: `pnpm run typecheck`/`test` clean in `packages/core` (33/33, including the 4 new crypto tests) and `packages/migration-tool` (44/44, unaffected by the refactor); `pnpm run typecheck` clean in `core-api`; `pnpm run build` (`vue-tsc` + `vite build`) clean in `admin-dashboard`. **Not verified**: no real browser click-through and no live run against a real Pimcore MySQL instance/filesystem in this environment (same stated gap as every prior UI/migration phase) - the refactored `runClassMigration`/`runObjectMigration` carry the exact logic Phase 3/6 of the sibling plan already proved against 202 real objects, but that proof predates this refactor's parameterization and hasn't been re-run against a live source since.

## 4. Explicit relationship to `advanced-data-modeling-plan.md`

- **Schema**: this plan adds exactly one nullable column (`data_classes.viewConfig`, §3.3) to that plan's §4.1 `data_classes` table. `data_objects` (§4.2) is untouched - native objects use the identical `attributes` JSONB shape migrated objects do, validated by the identical `compileDynamicSchema()`.
- **Relation engine**: reused as-is (§3.2) - this plan adds an authoring UI in front of it, not a new engine.
- **Migration pipeline**: stays exactly as that plan left it (Phases 0-7, DONE) - §3.4 wraps it, doesn't change it.
- **Permissions**: reuses `OBJECTS_READ`/`OBJECTS_WRITE` as-is for class CRUD, matching that plan's own Phase 1 correction (no new `"classes:write"` string, §7 of the sibling plan already walked this back once).

## 5. Open questions, stated rather than assumed

- **Does v1 need `fieldcollections` authoring at all?** Every real Field Collection type today comes from `migrate-classes` parsing real Pimcore PHP definition files (`advanced-data-modeling-plan.md` §5.1/Phase 6) - there is no native equivalent of "define a new named, reusable repeatable block type" anywhere in this plan. A customer with no Pimcore history who wants Product-style banner/slider blocks would need this eventually, but it's a real, separate authoring surface (define the type's own field list once, then allow it as one of several `collectionTypes` on a `fieldcollections` field) - deliberately deferred out of this plan's v1 rather than bolted on as an afterthought.
- **`block`-type fields in the Class Builder**: same shape of question as above but smaller - a recursive sub-field editor is buildable (the rendering side already recurses, `DataObjectForm.vue`'s own note in the sibling plan's Phase 2), just not included in §3.1's v1 list. Real v2 candidate once the flat-field case ships and is used for real.
- **Field-rename/delete guardrail (§3.1)**: v1's answer is "block the change outright." A future, friendlier answer (e.g. a real data-migration-on-field-rename tool) is explicitly not designed here - noted so it isn't mistaken for an oversight.
- ~~§3.4's credential-storage question~~ - resolved (§3.4): admin-entered, stored settings, encrypted at rest via a new AES-256-GCM utility rather than following this codebase's own weaker `users.totpSecret` plaintext precedent - chosen deliberately given this secret's larger blast radius, not by default.

## 6. Proposed phases

- **Phase 1 - Class Builder core: DONE.** `createDataClass`/`updateDataClass`/`deleteDataClass` added to `data-classes-api.ts` (thin wrappers over the already-real `POST`/`PATCH`/`DELETE /data-classes` routes, §2's own finding that these existed with no caller) and to `dataClassesStore.ts` (each mutation refetches the list afterward, matching the store's existing "no second source of truth" convention). New `ClassSettingsCard.vue`, wired into `SettingsView.vue` alongside `WorkflowSettingsCard.vue` (same placement/visual pattern - a class list with Edit/Delete, an inline editor for name/label/fields, ↑↓ field reordering, no drag-and-drop, matching that card's own precedent). Field editor covers the full v1 type list from §3.1 (`input`/`textarea`/`wysiwyg`/`numeric`/`checkbox`/`date`/`email`/`country`/`select`/`multiselect`/`manyToOneRelation`/`manyToManyRelation`/`link`), with `options` (comma list) shown for `select`/`multiselect` and a `relationTarget` class-picker shown for the two relation types - so **Phase 2's relation-authoring goal shipped as part of Phase 1**, since §3.2 already established the relation engine needed no new work, only a picker, and building that picker as a separate pass from the field editor it lives inside would have been artificial.
  - **Guardrails, implemented server-side (not just UI-side) so they hold regardless of caller**: `DELETE /data-classes/:id` now checks `listDataObjects(classId)` first and returns `409` if any objects exist, rather than deleting a class out from under real data (`deleteDataClass` itself has no cascade - `data_objects.classId` is a plain `uuid`, not a Drizzle FK, per the sibling plan's own Phase 1 note). `PATCH /data-classes/:id` now diffs incoming `fields` against the stored class's own fields *when objects exist*: a field disappearing (by `name`) or an existing field's `fieldType` changing is rejected with `409` and a message naming the offending field(s); adding new fields or editing `title`/`mandatory`/`localized`/`options` on a same-name-same-type field is unrestricted. `ClassSettingsCard.vue` surfaces the live object count (via `fetchDataObjects`) as a warning while editing, but the actual enforcement is the server's, not a client-side-only check.
  - Verified: `pnpm run typecheck`/`test` clean in `packages/core` (29/29 existing tests unaffected); `pnpm run typecheck` clean in `core-api`; `pnpm run build` (`vue-tsc` + `vite build`) clean in `admin-dashboard`. **Not verified**: no real browser click-through (no headless browser available in this environment, the same stated gap every prior UI phase in this plan family has - `advanced-data-modeling-plan.md` Phase 2/7's own precedent) and no live-database exercise of the new `409` guardrail paths against a real class with real objects.
- **Phase 2 - Relation authoring: DONE, shipped as part of Phase 1** (see above) - the relation-target dropdown landed inside the same field-editor pass rather than as a separate phase, since it's one control inside the Phase 1 editor, not an independent surface.
- **Phase 3 - Custom CRUD views: DONE.** `ClassViewConfig` (`{ listColumns?, detailSections? }`) added to `packages/core/src/schema/dynamic.ts`; `data_classes.viewConfig` (nullable `jsonb`) added via a single additive migration (`drizzle/0012_groovy_catseye.sql`, `ALTER TABLE data_classes ADD COLUMN view_config jsonb`) - every existing row keeps `NULL`, so every previously-migrated class renders exactly as before until an admin opts in. `data-classes-records.ts`/`server.ts`'s `POST`/`PATCH /data-classes` thread `viewConfig` straight through (`PATCH` accepts `null` to explicitly clear a layout, `undefined`/absent leaves it untouched, matching that route's existing per-field-optional convention).
  - **`DataObjectForm.vue`**: when `viewConfig.detailSections` is present, fields render grouped under named headings (a trailing "Other fields" heading catches anything left unassigned - §3.3's own "never silently hidden" requirement); absent, the original flat `v-for` renders unchanged - kept as a separate `v-else` branch rather than unified into "one untitled section," so the common case (every class today) isn't paying for indirection it doesn't use. `MasterObjectTab.vue` passes `dataClass.viewConfig` through.
  - **`ObjectsView.vue`**: gains extra table columns from `selectedDataClass.viewConfig.listColumns`, resolved back to their field definitions for display titles - only rendered once a single class is selected (same reasoning §Phase 7 already established for the per-field filter inputs: "field" has no meaning across classes). A small `formatListValue()` handles the shapes real attribute values actually take (relation `{id}` → the id, arrays → comma-joined, everything else → `String()`) - not factored out into a shared module with the CSV/XLSX/JSON export code, since that export path still does its own plain `String()`/raw-passthrough and never developed the richer per-type formatting §3.3 speculated it might already have.
  - **`ClassSettingsCard.vue`**: gained a "View Layout" section - an ordered checkbox list per field for list columns (order re-derived from field order on every toggle, not authored separately) and a named-section editor for the detail form (add/remove section, per-section field checkboxes; a field checked into one section is automatically unchecked from any other, so nothing can render twice) - no drag-and-drop, consistent with every other "not required for v1" editor in this codebase. On save, `buildViewConfigPayload()` drops any reference to a field that was renamed/removed in the same edit session and any section left with no title or no fields, collapsing to `null` (not an empty-shaped object) when nothing real remains configured - so an admin who opens this section, changes their mind, and saves doesn't leave a stale empty layout behind. No hard cap on how many columns/sections an admin can add - left to the author's own judgment rather than an invented limit (§3.3's own "not fixed here" on this point).
  - Verified: `pnpm run typecheck`/`test` clean in `packages/core` (29/29, `packages/core` rebuilt via `pnpm run build` so `core-api`'s typecheck picked up the new exported types/columns - a real step, not optional, since `core-api` resolves `@pimcore-custom/core` against its compiled `dist/`, not source) and `packages/migration-tool` (44/44, unaffected); `pnpm run typecheck` clean in `core-api`; `pnpm run build` (`vue-tsc` + `vite build`) clean in `admin-dashboard`. **Not verified**: no real browser click-through and no live-database migration run (same stated environment gap as Phase 1/every prior UI phase).
- **Phase 4 (optional, lower priority) - Admin-triggered Pimcore import: DONE.** See §3.4 for the full write-up - `migration_sources` table with AES-256-GCM-encrypted credentials, `runClassMigration`/`runObjectMigration` extracted from the CLI for reuse, `core-api` CRUD + import routes, and a new `MigrationSourcesCard.vue` (a separate settings card, not folded into the Class Builder as originally sketched - §3.4 explains the deviation).
